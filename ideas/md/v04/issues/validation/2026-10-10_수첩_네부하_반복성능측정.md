# 수첩 네 부하의 반복 성능 측정

## 1. 결론과 범위

T24a의 **고정 입력 HEADLESS 반복 측정**을 완료했다. develop `18a8841f4f6ef879ffc87ab558deab8cced1a963`의 원본 제품 640파일과 공식 4.6.3 후보로 PCK를 만들고 네 fixture/한영 각각 새 프로세스 20회, 첫 프로세스 안에서 warm 100회를 실행했다. 160개 native 프로세스와 800회 내구 저장은 모두 종료 0/기능 검사 PASS다. 재실행 없이 각 원자료를 보존했다.

**성능 합격은 아니다.** L10000의 첫 검색 p95는 한국어 1,448.236ms/영어 1,332.871ms, 실제 내구 저장 p95는 3,105.715ms/2,991.098ms다. 원문·보호·미분류 보존을 유지한 상태에서도 지연은 남는다. ERR-0027은 IN_PROGRESS, 제품 4.7/기본 rollout OFF와 엔진 채택·전체 인수 미완료를 유지한다.

게임 코드·기존 fixture·계측기를 수정하지 않았다. 이번 산출물은 반복 원자료, 독립 집계기, 남은 구현의 우선순위다. 실제 입력부터 비동기 host가 첫 목록을 공개하는 인수, 마우스/키보드 전편, GPU/배율/200%/IME/Alt+Tab·메모리 회수는 이 결과로 대체하지 않는다.

## 3. 입력 분모

| fixture | normal | protected | legacy | 책갈피 / 비교 | 문서·직렬화 부하 |
| --- | ---: | ---: | ---: | --- | --- |
| N2000 | 2,000 | 6 | 0 | 0 / 3 | 1,815,265 UTF-8 bytes |
| L10000 | 2,000 | 6 | 10,000 | 0 / 3 | 5,434,278 UTF-8 bytes |
| P2001 | 2,001 | 2,001 | 0 | 50 / 12 | 3,692,933 UTF-8 bytes |
| LONG | 1,980 | 26 | 0 | 0 / 3 | 20개 공개 다중 페이지, 각각 32,768 bytes; 전체 2,472,815 bytes |

전체 크기는 archive+ledger의 정규 JSON이다. LONG의 20개 문서는 보호되므로 normal과 별도로 센다. 공통 보호 6개에는 선택·요청한 H1·B4/C5/D4가 있다. 네 입력은 기존 `ggb-notebook-perf-v1` seed/해시를 고정했으며 모든 cold 프로세스와 두 언어에서 동일하다. 독립 검사도 입력 해시뿐 아니라 위 실제 분류 수·바이트·참조 수를 대조한다.

native probe는 append/prune 뒤 일반 상한만 적용되고 보호/legacy는 유지되는지, 영속 저장/reload의 snapshot이 같은지, 미공개 뒷면 sentinel 및 요청하지 않은 H2~H5가 검색에 들어오지 않는지 검사했다. 시험 모델과 GameState의 불변도 확인했다. 이 fixture 검사를 본편 생산자 전수/실제 발생의 증명으로 확대하지 않는다.

## 4. 측정 경계

- cold: 매번 새 OS 프로세스. fixture 생성/JSON parse 뒤 query.open부터 직접 패널을 표시한다. OS 디스크 캐시는 비우지 않았다. 실제 슬롯 로드/host 비동기 진입과는 다르다.
- 모델→패널: query 검증·생성, 첫 페이지, 실제 1280×720/글자 100% 패널 구성·두 프레임·포커스를 포함한다. 실제 입력/host 슬롯 확인의 수첩 냉간 예산과 동일한 지표가 아니다.
- 첫 검색: 검색칸의 text_changed부터 200ms debounce와 최초 공개 색인이 끝날 때까지. 실제 물리 키/IME 입력이나 GPU 렌더링은 아니다.
- warm 페이지·필터·일치/불일치/긴 검색·비공개 검색: 첫 프로세스에서 각 100회 모델 API만 측정한다. debounce/Control 구성/물리 입력은 제외되므로 warm UI p95 합격으로 사용하지 않는다.
- 내구 저장: 실제 `save_snapshot` 호출 시작부터 영속 성공 응답까지 100회. fixture append/prune는 별도 지표다. 실제 플레이 중 입력 프레임을 캡처한 것은 아니다.
- RAM: 프로세스 peak working set 표본. 열기 전/닫은 뒤 증분, 캐시 회수, 50회 open/close/60초 입력 프레임의 대체가 아니다.

전체 native 벽시계 합계는 약 2,792.35초다. 평균·최대·첫 회와 모든 시료는 [summary](evidence/2026-10-10_perf_repeats/measurements/summary.json)에 있다. p95는 각 지표를 정렬해 `ceil(0.95*n)`번째를 고른다. cold 지표 n=20, warm 저장/모델 지표 n=100이며 inspect 일부 지표의 다른 반복 수는 별도 유지한다.

## 6. 원자료와 독립 확인

[evidence](evidence/2026-10-10_perf_repeats/)에는 489개 원자료의 SHA/바이트 [manifest](evidence/2026-10-10_perf_repeats/manifest.json), 각 native stdout/stderr/result, summary·소스·장비·build 로그가 있다. 별도의 checks.json은 파생 검사 결과다. 사용자의 실제 세이브와 큰 PCK를 Git에 넣지 않는다. 보관 PCK를 이동했다면 validator의 `-PackPath`로 지정한다. 부재를 PASS로 처리하지 않는다.

독립 집계는 160개의 native 결과와 원래 result.json/summary를 대조하고 fixture/locale·cold 이름·warm 수·엔진/PCK·원본 640파일·원시 로그·입력 크기를 검사한다. 각 그룹의 first/mean/max/nearest-rank p95와 process peak를 다시 계산한다. sample 수 축소/누락 cold/중복 프로세스/잘못된 p95/native 실패/변조 raw SHA의 6반례를 모두 거부했다.

초기 독립 검사에서 Hashtable의 집계 순서에 따라 반례가 중단되는 위치가 달라 검사 카운터만 26,640/26,628로 달랐다. 원시 시간·통계·PASS/반례 결과의 차이는 아니다. 지표 키를 정렬해 카운터를 안정화했으며 최종 [checks](evidence/2026-10-10_perf_repeats/checks.json)를 따른다. 성공 횟수를 기능 조합 수로 합산하지 않는다.

```powershell
./scripts/audit_notebook_performance_repeats.ps1 `
  -EvidencePath ./ideas/md/v04/issues/validation/evidence/2026-10-10_perf_repeats `
  -SelfTest
```

기존 재현 명령은 `measure_notebook_performance.ps1 -GodotPath <후보> -PackPath <격리PCK> -ColdRuns 20 -WarmRuns 100`이다. 새 빈 출력 디렉터리를 사용한다. 검사기의 고정 baseline은 이 보고서의 source commit이며 다른 코드의 시간을 같은 근거로 대체하지 않는다. 엔진 minor 경고는 그대로 보존했고 native 프로세스는 모두 정상 종료했다.
