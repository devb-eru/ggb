# 공식 4.6.3 최신 커밋 기능 호환 검증

## 목적과 판정 범위

기준 develop `058b2401187f1722eb96d1aceb7d11be5c6b965b`. [이전 후보 재검사](2026-10-07_공식4.6.3_최신코드_호환재검증.md)의 시간 제한/결과 소실을 PASS로 바꾸지 않고, 갤러리 헤더 보호와 strict fixture 수정까지 반영한 현재 커밋을 재검사한다. T22f2의 자동 기능 호환 작업이며 엔진 전체 채택이나 실제 입력 완주 인수가 아니다.

제품은 Godot 4.7·기본 rollout OFF를 유지한다. Steam 설치·에디터 템플릿·사용자 세이브·Windows 입력기 설정은 변경하지 않는다. 기존 실제 게임 IME 다섯 정상 조건도 [공식 비교 기록](2026-10-06_한글IME_공식런타임_비교.md)의 역사적 국소 근거로 보존하며 이번 새 실제 입력으로 집계하지 않는다.

## 공식 배포와 격리

- [공식 release](https://github.com/godotengine/godot/releases/tag/4.6.3-stable)의 API에서 release ID `326249817`, Windows x64 asset ID `425559552`, 79,844,616 bytes를 조회했다.
- `Godot_v4.6.3-stable_win64.exe.zip`의 공식 digest와 다운로드 SHA-256: `e39986a178d585ce7ac198fb8de6ea436366dc0cc00e594810c2e3e104c04b90`.
- 실행 파일 SHA-256: `ef90e929ba1a6a4322860285d97f40f4aa349c90329a91b0e8b55b8df0f4cb00`. import 로그의 버전은 `4.6.3.stable.official.7d41c59c4`다. 이전 공식 후보와 같은 ZIP/실행 파일임을 확인했다.
- 새 TEMP `ggb-463-final-compat-76e7003a7f044925bc3ba04c87e15d57`에 엔진과 현재 Git 아카이브의 `game`, `scripts`, `.gitattributes`를 준비했다. 기존 TEMP 경로나 결과를 덮어쓰지 않는다.
- Git 원본 게임 파일 640개의 경로·바이트 수·SHA가 import 이후에도 일치한다. 새로 생성된 테스트 `.gd.uid` 4개는 별도 목록으로 보존하며 `.godot` 캐시와 원본을 혼동하지 않는다.
- 현재 GDScript 264개 SHA-256 `08fb92454227daf678824f2721f8a5946b8ecce002c03bd7b74cdb13bb991708`, data 52개 코호트 SHA-256 `af1ff4a6fb3c427b8dbc22ea273e2b57904252338e392a05abdb40b8a735660a`.

검사마다 APPDATA/LOCALAPPDATA를 새 경로에 지정한다. engine child는 Hidden/headless로 실행하며 장시간 final/캠페인은 단독 순차 실행·3,600초 watchdog을 적용한다. 제한 시간에 도달하면 해당 runner의 자식만 종료하고 실패 receipt를 남긴다. 동작을 빨리 통과시키기 위해 테스트 분기·strict 옵션·저장 검증을 생략하지 않는다.

기존 bootstrap의 `GGB expects Godot 4.7.x` 경고를 숨기거나 기대 버전을 넓히지 않는다. 현재 final 로그에 이 알려진 경고가 있다. 실제 script/parse/compile/error는 별도로 실패 처리한다. 실행 시간은 호환 검사 부하이며 엔진 간 성능 비교 자료가 아니다.

`final` 독립 trace 대조는 858개 고유 관찰 경로, 원장 표본 authored 2,674 / legacy 0 / unmapped 0이다. 등록 문단의 표본 대조이며 신규 유입 전수·제외 UI·독립 필수 분기는 여전히 미감사다. 캠페인은 trace 옵션을 전달해도 기존 runner가 `NOTEBOOK_RUNTIME_AUDIT`를 출력하지 않으므로 이 합집합에 포함하지 않는다. 캠페인의 실제 native PASS와 final의 관찰 기록을 분리한다.

프롤로그의 408개 고유 관찰 경로와 final의 같은 소스 trace 두 개를 독립 감사하여 합집합 1,266경로를 확인했다. 다른 소스의 과거 21suite·캠페인과 합산하지 않는다. PCK는 17,894,004 bytes, SHA-256 `2e50c4ab3571fd41a28a58b1a4dd7e385057011e452b40b03e0199dc2d02e1fe`이며 pack-foundation receipt도 같은 바이트 수/hash다.

첫 독립 검사 래퍼에서 `-SelfTest`를 정상 JSON 감사와 혼용했던 오류를 별도 텍스트로 보존했다. 정상 감사는 옵션 없이 다시 실행하여 `ok=true`, errors 없음과 소스 264개를 확인했고, selftest도 별도로 PASS했다. PowerShell의 초기화되지 않은 `$LASTEXITCODE`를 게임 실패로 판정하지 않는다.

## 근거와 재현

`evidence/2026-10-10_463_final_` 접두사로 공식 asset 메타데이터, Git 원본 source guard, 실행별 stdout/stderr/receipt를 보존한다. 완료 전 일부 로그를 최종 receipt인 것처럼 저장하지 않는다. 각 receipt는 native 종료·strict/rollout 옵션·엔진/runner/로그 hash·시작/종료 코드/data 코호트 불변을 기록한다.

```powershell
./scripts/run_notebook_candidate_compatibility.ps1 `
  -EnginePath <공식_SHA를_검증한_임시_실행파일> `
  -ProjectPath <현재_커밋의_새_TEMP_game> `
  -EvidencePath <아직_없는_TEMP_증거폴더> `
  -Mode final -TimeoutSeconds 3600
```

동일 runner의 campaign-v2/campaign-ordinary는 새 증거 폴더로 각각 실행한다. pack에는 신규 TEMP `-PackPath`를 지정하며 pack-foundation에서 그 PCK를 사용한다. 실제 사용자 프로젝트·profile 경로를 직접 지정하지 않는다.

관련 회귀는 `producer-contract`, `prologue-surfaces`, `migration`, `query`, `host` 모드다. 첫 여섯 실행 중에는 runner를 수정하지 않고 v1을 증거 폴더의 `2026-10-10_463_final_runner_v1.ps1`로 보존했다. 배치 종료 후 보조 모드를 추가한 v2 runner로 다섯 실행을 완료했다. runner hash 변경과 동일 제품 코드/data의 불변을 구분한다. 갤러리는 기존 `run_notebook_gallery_future_audit.ps1`와 기존 외부 fixture를 수정 없이 사용한다.

`audit_notebook_candidate_compatibility.ps1`는 receipt·원자료 SHA·실행 옵션/실제 버전·v1/v2 runner·원본 640개와 스크립트/data 코호트·trace의 29카탈로그를 대조한다. `-SelfTest`의 유효 control과 종료 실패/미완료/strict OFF/v2 OFF/다른 mode/다른 engine/다른 runner/로그 변조/소스 변경의 9개 반례는 모두 거부했다. `audit_notebook_runtime_union.ps1`의 기존 selftest는 별도로 실행했다.

최종 독립 대조는 [검사 결과](evidence/2026-10-10_463_final_checks.json)의 12receipt·1,435확인 모두 PASS다. 갤러리 324개 키의 독립 분모·중복/누락·원본 바이트 불변과 raw/저장 summary·기존 외부 fixture/checkpoint/store hash도 대조했다. trace 합집합은 [원자료 대조](evidence/2026-10-10_463_final_runtime_union.json)에서 재현할 수 있다. import/final/두 캠페인/pack/기본 실행 및 관련 회귀/갤러리의 소유 프로세스 12개는 모두 종료했다.

각 검사의 관찰 수를 단순 합산해 전체 인수량으로 만들지 않는다. query/host 하위 계측은 반복 단언 수가 실행 대기 경로에 따라 달라질 수 있으며 다른 엔진의 이전 총수와 같아야 한다는 조건이 아니다. 실제 native 결과·실패 목록·명시된 분모와 소스 동일성으로 판단한다.
