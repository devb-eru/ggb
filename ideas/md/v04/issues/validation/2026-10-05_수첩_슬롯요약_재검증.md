# 수첩 슬롯 요약의 재검증 비용 보완

## 범위와 판정

- 기준: `develop`의 `dd5f962b2f962e7cc74f87695c6ce59c58a8ba6d`.
- 연결 오류: [ERR-0027](../items/GGB-ERR-2026-0027_대용량_수첩_표시검색저장_지연.md).
- 이번 범위: 슬롯 표시용 요약의 중복 검증, 자료 고정 명령의 중복 슬롯 조회. 실제 저장을 비동기화한 변경이 아니다.
- 전체 상태: **IN_PROGRESS**. 첫 화면·최초 검색·실제 저장의 지연, 실제 Windows 입력·IME, 장비별 성능 인수는 남아 있다. 기본 rollout은 비활성 그대로다.
- Windows 잠금 해제 응답이 없어 실제 키·마우스 입력은 재개하지 않았다. 아래는 격리 APPDATA와 빈 runtime 디렉터리의 export PCK headless 검사다.

## 원인과 변경

`notebook_commands.gd::set_reference`가 scope 확인과 저장 지점 조회를 위해 같은 슬롯을 두 번 검사했다. 각 `inspect_slot`은 전체 파일의 JSON 파싱, 서명 확인, 정규화와 snapshot 검증을 반복했다. 수첩의 프레임별 `_same_live_scope`는 이 디스크 검사를 호출하지 않으므로 프레임마다 전체 파일을 읽었다고 해석하지 않는다.

1. 명령은 한 번 검증한 슬롯 요약으로 scope와 저장 지점을 함께 판단한다. 낡은 load epoch·revision·사용 불가 슬롯 거부 및 저장 실패 롤백·성공 응답 소실 확인은 유지한다.
2. `SaveManager::_inspect_file`은 **매번 실제 파일 바이트를 읽고 SHA-256을 계산**한다. 파일 시각·크기·헤더에 적힌 checksum만으로 동일성을 추정하지 않는다.
3. 같은 절대 파일 경로·이관 모드·바이트 지문일 때만 검증된 표시 메타데이터를 재사용한다. 변경된 파일은 기존 검증기 전체를 다시 거친다. checksum 오류, 미래 버전, 손상 결과를 정상 캐시로 보존하지 않는다.
4. 캐시는 최대 8개 LRU이며, 각 요약의 JSON UTF-8 크기가 4,096바이트를 넘으면 저장하지 않는다. 이 수치는 요약 보존 제한이지 전체 게임 RAM 상한이 아니다. snapshot·원문·파일 바이트는 캐시에 남기지 않고 반환 메타데이터도 복제한다.
5. `_read_and_validate`의 파싱 본문은 `_validate_save_text`로 분리했다. 실제 저장·불러오기·백업·임시파일·commit 확인은 표시 캐시를 사용하지 않는다. 디스크에 영속 성공하기 전 성공으로 표시하는 변경이나 schema 변경은 없다.

## 회귀 확인 범위

`notebook_save_safety_smoke.gd`에 다음 반례를 추가했다. 기존 서명 바이트·구형 이관 ID·손상 본파일과 정상 백업·승격 실패/복구 검사도 유지한다.

- 최초 요약은 전체 검증, 불변 파일 재조회는 검증 재사용, 호출자에 의한 반환 객체 변경은 다음 조회에 영향 없음.
- 정상 캐시가 있어도 전체 상태 읽기와 저장 시 본파일·백업·임시파일 각각을 독립 검증.
- 같은 길이의 외부 변경과 기존 checksum 조합을 거부하고 정상 백업으로만 fallback. 조회 자체는 어느 파일도 복구/수정하지 않음.
- 외부의 유효한 다른 run/save point 파일 교체를 즉시 반영.
- 미래 버전 본파일은 정상 백업으로 fallback하지 않음. 미래 백업은 본파일 요약이 정상이어도 실제 저장을 막음. 원본 바이트 보존.
- 파일 삭제 시 캐시 제거, 재생성 시 재검증. 경로별 LRU 8개 상한·오래된 항목 축출·4KiB 초과 요약의 비보존.
- 명령 경로에서 scope와 저장 지점에 정확히 한 번의 `inspect_slot` 사용. 기존 이관 검사의 저장 실패/재시도·성공 응답 소실·F3/demo/full/갤러리 회귀 유지.
