## 2. 재현과 수정

새 물리 리셋은 `M1_BEDROOM`을 만들지만 설치된 방은 `M2_BEDROOM`이었다. `initialize()`가 아직 설치하지 않은 후보 위치만 교정하고, 신규 피드백의 기본 출처는 교정 전 live snapshot에서 가져왔다. 실제 `NB_CH1_WAKE` 관찰과 커서의 출처에도 구형 ID가 기록됐다.

수정된 기준 검사기의 별도 프로세스 chapter/idle/promoted/ko→en 실행은 native 1과 네 실패를 반환했다. 물리 후보·피드백·표시 커서·실제 authored 관찰의 위치 불일치를 각각 확인했으며, 이 재현의 스크립트 오류는 없다.

| 파일 | 수정 | 보존하는 규칙 |
| --- | --- | --- |
| `reset_coordinator.gd` | 새 정상/파열 물리 리셋의 위치를 `M2_BEDROOM`으로 생성 | 일차, 단계별 저장, transaction·영구 데이터 보존 |
| `chapter_one_session.gd` | `stage(state)`/`history_context(state)`로 명시 후보를 읽음. 기존 피드백이 없는 초기화만 정규화 후보의 출처 사용 | 기존 `last_feedback`/legacy 출처는 그대로 재생. 일반 행동은 행동 전 문맥 유지 |
| `black_mirror_session.gd` | 후보 snapshot을 받는 상속 stage 계약 | 기존 인자 없는 호출의 동작 |
| `basement_session.gd` | 첫 E1 피드백 및 사건 원고에 후보 문맥 전달. 루카 분기 판단도 같은 snapshot 사용 | 일반 파열 행동의 기존 출처/보상·관계 조건 |
| `basement_session_smoke.gd` | stage 재정의의 선택 snapshot 인자 수용 | 엔딩 저장 실패 검사의 기존 강제 stage |

스키마나 기존 저장의 역사적 출처를 일괄 이관하지 않는다. 실제 원문을 읽은 위치가 구형 ID였다는 사실과 현재 게임의 정본 위치를 별도로 관리한다.

## 3. 동기·비동기 초기화

검사: `run_notebook_campaign_sleep_audit.ps1 -Mode location`.

4세션(chapter/mirror/basement/첫 E1) × 2위치(M1/M2) × 2종(신규/기존 피드백) × 2초기화(동기/worker) × 2언어 = 64조건, 9,184단언, native 0.

- 새 위치 정규화뿐 아니라 실제 controller의 표시 대사, authored 관찰, 커서를 검사했다.
- 첫 E1 사건 원고의 위치·노드·장은 `M2_BEDROOM`/`E1_ENTRY`/`CHAPTER_3`이다.
- 기존 M1 피드백은 과거 M1 출처를 유지하며 UID·원문·보호·책갈피·비교 참조가 보존된다.
- 저장 로드와 재열람에서 원장·커서가 같고 중복 관찰이 추가되지 않는다.
- 같은 프로세스의 로드 검사이며, 별도 프로세스나 실제 OS 입력으로 집계하지 않는다.

## 4. 별도 프로세스 검증 설계

| 묶음 | 조건 | 종료/복귀 의미 |
| --- | --- | --- |
| 새 코드 132좌표 | P6·본편·거울·지하·D6 침실/캡슐, 정상/파열 8단계, 물리 후보 승격 전, wake 승격 전후·한영 | 실제 저장 작업의 지정 경계에서 seed 자식을 종료하고 새 프로세스로 재개/재열람 |
| 구형 idle alias 16좌표 | 4세션 × 신규/기존 원문 × 한영 | 검증된 구형 저장 fixture의 seed 프로세스를 종료. reset worker 중단으로 계산하지 않음 |
| 기존 코드의 보류 리셋 32좌표 | 정상/파열 × 8단계 × 한영 | 실제 기존 코드의 seed 저장을 종료한 뒤 새 후보로 재개/재열람. seed와 recovery의 소스 지문이 다름을 명시 |

각 복귀에서 남은 단계만 실행, 정확한 일차·transaction, live/디스크 일치, 두 번째 복귀의 전체 snapshot 불변 및 원문/관계/참조 보존을 확인한다. 기준/후보 제품 265개 스크립트 지문, 엔진·실행한 검사 장치·로그·cut·snapshot의 SHA를 연결한다.

완료 좌표만 집계한 복귀/재열람 단언은 새 코드 132좌표 58,946개(비휴식 128좌표 56,458개 + 휴식 네 좌표 2,488개), 구형 idle alias 16좌표 7,530개, 기존 코드의 보류 reset 32좌표 14,576개다. 총 180개 체인/81,052개 단언이다. 체인별 seed·resume·verify의 540개 프로세스 수명 중 의도적 종료는 reset 경계 164개와 구형 idle fixture 16개이며, 정상 복귀/재열람은 native 0 360개다. 아래 독립 감사 및 일반 회귀 실행은 이 분모에 합치지 않는다.

## 5. 미승격 휴식의 예외

파열 후 휴식은 새 물리 리셋이 아니다. POST_REST 후보를 승격하기 전에 종료하면 기존 저장의 마지막 피드백을 다시 열 뿐, 아직 관찰하지 않은 POST_REST나 새 E1을 작성하면 안 된다.

검사 fixture에는 출처 없는 구형 E1 피드백이 이미 있다. 그 경우 `LEGACY_UNKNOWN` 문맥과 `legacy_feedback_origin`의 실제 원문을 유지하고 새 authored 기상 건수는 0이어야 한다. 현재 방의 `M2_BEDROOM`은 이 원문의 출처를 M2로 소급 교체할 근거가 아니다. 수정된 네 휴식 좌표는 native 0 복귀/재열람으로 통과했다.

## 6. 실패 시도와 집계 원칙

1. 최초 기준 검사기의 커서 최상위 `history_context` 가정은 잘못됐다. 실제 구조는 `lines[].history_context`이며 원래 실패 로그를 보존한다.
2. 새 64조건 검사기의 동적 session 반환값 타입 추론 오류는 `candidate_context: Dictionary` 표기로 교정했다. 첫 parse 실패를 성공에 합산하지 않는다.
3. 초기 휴식 표본은 미승격 구형 피드백을 새 authored 기상으로 취급해 실패했다. 새 출처의 M2 계약은 유지하고, 기존 원문의 재분류 금지 조건을 별도로 검사한다.
4. 초기 표본 및 전체의 이전 휴식 검사 결과와 수정된 마지막 네 좌표를 구분한다. 같은 제품 소스라는 이유로 실패한 검사 장치의 실행을 소급 PASS로 바꾸지 않는다.
5. 첫 봉인 스크립트는 검사 상대 경로가 아니라 절대 경로에서 `AppData`를 제외해 원자료까지 비우고 복사 단계에서 중단됐다. 제외 기준을 검사 폴더 내부의 `profile/appdata/localappdata` 상대 경로로 교정했다. 이 중단은 독립 감사 실행이나 제품 검사 실패로 집계하지 않는다.

## 8. 추가 지하 통합 검사와 제한

개발 수첩 모드의 추가 지하 검사는 native 1/13,543실행 단언, 실패 목록 38개 및 필드 버튼 null 접근을 반환했다. 수정 전 기준본도 native 1/13,543개이며 실패 38개의 순서·문구가 모두 같아 이번 위치 수정의 완료와 분리한다. 원자료의 `before-basement-v2-candidate`와 `before-basement-v2-baseline`을 보존하며 [ERR-0069](../items/GGB-ERR-2026-0069_지하통합검사_수첩준비완료_대기누락.md)에 원인 후보·안전한 검사 개선·재검증을 추적한다.

최초 후보 진단 영수증에는 이후 추가한 `mode`/`baseline` 필드가 없다. 이를 사후 채워 실행 당시 기록인 것처럼 만들지 않는다. 소스·로그·엔진 SHA와 실제 실패 목록은 보존하지만 이 진단 실행을 엄격 모드 PASS나 성공 회귀 수에 포함하지 않는다. 뒤의 기준본 및 기본 모드 실행부터는 해당 필드를 실제 실행 시 기록한다.

추가 기본 모드의 후보와 수정 전 기준본 모두 행동 13,921단언/PASS/native 0이다. 하지만 각각 종료 시 WeakRef 다섯 개와 `process_frame` 고아 참조가 남아 무누수 회귀 기준은 실패했다. `before-basement-ordinary-candidate`와 `before-basement-ordinary-baseline`에 원자료를 보존하고 [ERR-0070](../items/GGB-ERR-2026-0070_지하통합검사_종료시_WeakRef누수.md)에 생성 경로·회수 검증을 따로 추적한다. 이 두 실행 역시 성공 회귀 수에 포함하지 않는다.
