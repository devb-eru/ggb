# 변수 템플릿 조각 캐시 검증

## 범위

- 기준 develop: `910a139517c509bd25eedc402a4a782b7b1c667c`.
- T20m: `notebook_content.gd`의 변수 치환에서 동일한 템플릿의 정규식 생성과 분해를 반복하지 않는다.
- 전체 T20/T24와 ERR-0027은 미완료다. 전체 검색 개선을 입증하지 못했고 rollout은 기본 비활성이다.
- 실제 게임 IME 다섯 국소 조건의 사용자 정상 확인은 T22d의 별도 근거다. 이 보고서의 headless 검사는 물리 입력이나 4.6.3 엔진 채택 근거가 아니다.

## 변경 계약

1. 템플릿 문자열을 키로 리터럴/변수 이름 조각만 보관한다. 변수 값, 언어, enum 번역, 관계나 공개 상태는 보관하지 않는다. 각 호출에서 현재 명세와 값으로 단일 패스 치환한다. 값 안의 중괄호는 다시 치환하지 않는다.
2. 바깥 배열과 내부 조각 쌍을 모두 읽기 전용으로 만든다. lookup/삽입/축출과 진단 snapshot은 별도 mutex로 보호한다. RegEx는 cache miss마다 호출자가 독점 생성하고 공유하지 않는다. 동시 miss에서 중복 분해는 허용하며 전역 1회 생성은 보장하지 않는다.
3. 최대 128개, 키 템플릿 문자 합계 131,072개를 유지한다. 8,192자를 초과하는 템플릿은 계산만 하고 보관하지 않는다. 오래 삽입된 키부터 축출한다. 이는 문자/항목 제한이지 RAM 바이트 제한이 아니다. 조각 배열과 문자열 복제의 실제 메모리 인수는 남는다.
4. 변수 명세가 없으면 기존처럼 원문을 그대로 반환한다. 카탈로그/관찰 전체 검증, 미공개 거부, 부분 공개, 구형 원문 fallback, 저장 형식은 바꾸지 않는다.
5. 테스트를 기존 content 회귀에 연결한다. `_compiled_template`는 내부 함수이고 `substitution_diagnostics()`는 값이 없는 계측 snapshot이다.

## 검증

- Windows 격리 source project, Godot `4.7.2.stable.steam.ed1daf0bf`. 각 suite는 별도 APPDATA/LOCALAPPDATA를 사용한다. 사용자 저장은 읽거나 쓰지 않는다.
- 집중 검사 170개 PASS: 기존 정규식 알고리즘과 한영 출력 동일성, enum/변수 내부 중괄호, Unicode/줄바꿈, 현재 값 재사용, 호출자 불변, nested read-only, 빈 명세, 큰 템플릿 미보관, 축출 한도, 8 worker × 100회 값 분리와 종료 확인.
- query PASS: 6,863개 단언. 내부 metadata 74,828개, 29개 카탈로그/1,736개 의미 정의 × 한영, 부분 공개 및 기존 scope/조회/비교/갤러리 회귀 포함. 생산자별 필수 실행 분기 전수는 아니다.
- content PASS: 60개 힌트 ID × 한영 120조건, NP20 현재 tuple 150/150, 과거 tuple 24개와 저장 거부·재시도 150경로/보조 16조건. 오류 배열은 비어 있다. 내부 집중 검사도 170개 PASS. 다른 생산자 전체 실행이나 실제 OS 입력은 아니다.
- 집중/query/content와 전후 네 perf 프로세스의 종료 코드 0 및 스크립트 오류 없음 확인. 테스트한 세 변경 GDScript의 SHA256은 제출 원자료와 일치한다.
- stderr의 `Failed to read the root certificate store` 경고는 스크립트 오류와 구분한다.

재현 옵션:

```text
<godot-console> --headless --path <isolated-project> -- --notebook-query-smoke --ggb-dev-notebook-v2
<godot-console> --headless --path <isolated-project> -- --notebook-content-smoke --ggb-dev-notebook-v2
<godot-console> --headless --path <isolated-project> -- --notebook-performance-probe --nb-perf-fixture=L10000 --nb-perf-locale=ko-KR --nb-perf-warm=1 --nb-perf-cycles=0
```

실제 perf 옵션은 아래 로그의 측정 metadata와 대조한다. 별도 집중 실행은 SceneTree runner가 `notebook_substitution_smoke.gd.run()`을 호출한다. content 실행에는 동일 검사가 내장되어 있다.

## 계측과 한계

같은 프로세스의 2,000행 ABBA 대조는 출력 배열 전체가 같다. 집중 실행에서 기존 알고리즘 21.085/21.525ms, 캐시 10.863/10.723ms였다. content 내부 반복 측정도 별도 로그에 남긴다. 이는 반복 템플릿 치환 경로에 한정된 탐색 측정이다.

| L10000, ms | 이전 한국어 | 이후 한국어 | 이전 영어 | 이후 영어 |
| --- | --- | --- | --- | --- |
| 첫 검색 전체 | 3,187.900 | 3,464.082 | 2,891.076 | 3,086.576 |
| 색인 CPU 합계 | 1,489.258 | 1,519.161 | 1,554.456 | 1,660.669 |
| 본문 처리 합계 | 834.321 | 850.307 | 866.860 | 916.703 |
| 공개 필드 처리 합계 | 318.177 | 322.551 | 310.561 | 333.616 |

네 실행은 동일한 fixture SHA256 `cb640d6a7d1956b796f09a9c8b8be6b7758f2e098b4c71841474e47560c624a8`를 사용하고 기능 오류 배열이 비어 있다. 전후 한영 각각 새 프로세스 1개/warm 1이며 정식 cold 20/warm 100, p95/최대, 실제 입력 지연 인수는 아니다. fixture가 구형 기록 10,000개를 포함하므로 authored 템플릿 재사용만으로 전체 검색 개선을 기대하지 않는다.

**전체 첫 검색은 두 언어 모두 증가했다.** 순차 단일 표본으로 회귀 원인을 캐시로 확정할 수는 없지만 전체 개선을 주장할 근거도 없다. 반복 분해 제거와 기능 동일성이 확인된 제한적 구조 개선만 유지하고 ERR-0027을 해결 처리하지 않는다. 정식 예산 검사에서 악화가 재현되면 캐시 유지 여부도 다시 판단한다.
