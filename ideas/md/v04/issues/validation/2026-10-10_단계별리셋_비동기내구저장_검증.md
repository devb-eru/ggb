## 내구 저장 계약

1. `prepare_step` 순수 builder가 동기·비동기 경로 모두에서 다음 단계 후보를 구성한다. 비동기 worker에는 분리한 Dictionary만 전달하며 Node/GameState를 worker에서 조작하지 않는다.
2. 리셋 단계는 `sleep_confirmed → player_committed → memory_committed → physical_reset_complete → morning_loaded → route_selected → complete → idle`이다. 사용자 세이브 포인트를 추가하지 않는다.
3. 후보 준비·검증·임시 파일 직렬화 후 SaveManager가 현재 슬롯/파일 바이트·revision·load_epoch·root/flavor·외부 guard를 확인한다. 승격 성공 또는 정확한 transaction/snapshot의 ACK 확인 뒤 live 상태를 설치한다.
4. 내구 성공 후에만 단계/완료 신호를 낸다. 실패한 단계를 live에 먼저 노출하거나 신호로 성공 처리하지 않는다. 단계마다 저장되므로 재시도는 마지막 내구 단계 다음부터 진행한다.
5. 리셋 전체의 시작 load_epoch와 기대 revision을 보관한다. 단계 성공 때 기대 revision만 하나 증가시킨다. 단계 신호의 콜백에서 로드 세대나 상태가 바뀌어도 다음 worker를 시작하지 않는다.
6. 프롤로그는 pending 동안 수첩·이동·중복 수면·메뉴/타이틀 경로를 막는다. 실패는 명시 재시도 버튼을 제공하며 자동으로 수면을 반복하지 않는다. 부팅 재개는 리셋 성공 뒤에만 캠페인을 연다.
7. 정상 리셋은 물리 상태와 소지품·지역 상태를 초기화하고 같은 침실/아침으로 돌아간다. 영구 지식·대화 원문/UID·관계/사용인 기억을 유지한다. 파열 리셋은 추가로 S3/broken 상태와 E1 경로를 확정한다.

## 발견·수정 및 실패 보존

- 초기 128조건 검사로는 worker 안의 stale만 확인하고 단계 신호 콜백 사이의 변경을 놓쳤다. 추가 8조건이 모두 실패하여 리셋이 물리 초기화까지 계속 진행됨을 확인했다. `archive/between-diagnostic`은 native 1·136조건·3,404단언·실패 8개/오류 16개로 보존한다. 리셋 전체 context guard 수정 후 같은 분모가 모두 통과했다.
- UI 첫 실행의 타입 추론 parse 오류, 두 번째 fixture의 잘못된 pending 식별/이전 writer 정리 누락을 보존한다. worker 종류가 reset인 시점까지 기다리고 이전 writer를 명시적으로 배출했다. 성공 조건이나 원문 보존 검사를 삭제하지 않았다.
- 최초 UI PASS의 resource/Tween 경고도 성공 로그와 함께 보존한다. actual reveal 1.4초 Tween이 끝나기 전에 fixture를 제거한 것이 verbose orphan/Tween으로 나타났다. 캠페인 writer와 reveal 종료를 기다린 최종 current-ui에서는 resource/ObjectDB 경고가 없다. 이것은 fixture 수명 수정이지 임의 노드 제거/강제 종료의 전체 수명 인수는 아니다.
- 과거 128조건·중간 회귀·진단 실행은 archive에 따로 둔다. 최신 수정본의 8회 합격 수에 더하지 않는다. 최초 runner가 따로 동결되지 않은 실행은 manifest의 원자료 보존 근거일 뿐, 최신 runner와 일치하는 재현 근거라고 주장하지 않는다.
