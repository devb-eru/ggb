# 공식 4.6.3 최신 Windows Release 배포 후보 검증

## 1. 결론과 범위

T22f3a의 release 빌드·명시 호환 경로를 완료했다. develop `f5ffcfb34e0ad82121592ee9b443f6a198b9f39e`의 확정 게임 640파일을 새 TEMP로 추출하고 공식 엔진·정확히 일치하는 release 템플릿으로 내보냈다. 순수 배포본의 일반 타이틀 시작과 별도 테스트용 release 패키지의 한영 각각 27단언, 최종 5receipt·7native 단계 및 독립 13,056확인·6반례 모두 PASS다.

게임 코드·카탈로그·제품 설정은 수정하지 않았다. 빌드 도구에 release 템플릿 명시 선택과 검증 경로를 추가했다. 순수 배포본의 시작과 테스트용 패키지의 내부 호환 검사는 다르며, 엔진 채택·새 수첩 rollout·전체 기능/OS 입력/성능 인수는 완료하지 않았다.

## 3. 두 패키지의 구분

| 패키지 | 변경 범위 | 확인 결과 |
| --- | --- | --- |
| production | 확정 제품 640파일, 원래 main scene 유지 | 실제 `--export-release`, 원래 타이틀 부팅, release의 foundation smoke 거부. 소스 없는 빈 working directory에서 native 0 |
| compatibility_test_only | 제품 코드 그대로, 테스트 Node/scene 추가 및 main scene 경로 한 곳 교체 | 같은 release 템플릿의 `OS.is_debug_build() == false`, 실제 제품 main scene을 내부에서 instantiate해 새 게임·이어하기·저장/기록 조회 검사 |

EXE SHA-256은 두 패키지 모두 `9635acd1df035f69a2102b500be25a7981cea70d5533d5e5e89c96cd149f67d5`다. embed_pck=false이므로 게임 리소스가 다른 것은 PCK로 구분한다.

- 순수 배포 PCK: `a9c1df94ae5897972a4c6068961109a971b311e6cb1b2d811b6540bd141fed0d`.
- 테스트 전용 PCK: `9ca3a8507ba696569b239862d1b02707f9f94b6ff8361f08fe731211013a7576`.

두 EXE/PCK는 서로 다른 `production`/`compatibility_test_only` 디렉터리에 보존했고 실제 보존 파일의 바이트 수·SHA를 독립 validator로 다시 확인했다. 보관 위치는 [artifact 목록](evidence/2026-10-10_release_candidate/artifacts.json)에 있다. 바이너리는 Git에 커밋하지 않는다. 테스트 패키지를 실제 배포본으로 전달해서는 안 된다.

원본 640파일은 모두 재대조한다. import가 원래 미추적이었던 `notebook_runtime_audit`, `notebook_scope_smoke`, `notebook_substitution_smoke`, `notebook_view_future_smoke`의 `.gd.uid` 네 개를 새로 생성했다. 최종 production receipt는 644파일이며 원본 640개 불변과 이 4개를 구분한다. 테스트 빌드는 import 전 642파일, probe는 위 4 UID와 테스트 스크립트 UID가 더해진 647파일이다. 추가 UID 원자료도 별도 보존했다. 다른 제품 코드 수정이나 추가 파일을 허용한 것이 아니다.

## 4. 실제 Release 호환 검사

각 probe 실행은 새 APPDATA/LOCALAPPDATA, `slot_01`을 사용한다. 사용자의 실제 `slot_01`이 아니라 격리 저장소다. 개발 v2 옵션·foundation smoke·개발 체크포인트 jump를 함께 전달해도 release gate가 열리지 않는지 확인한다.

1. 실제 제품 타이틀은 보이고 개발자 패널은 생성되지 않는다. `NotebookRollout.enabled()`는 false다.
2. 실제 `new_game_requested` signal로 프롤로그에 진입해 표시 대사를 기존 진행 함수로 완료한다. rollout OFF의 일반 이력이 저장되고 전 항목이 표시된다.
3. 실제 대화 기록 모달을 열고 닫아 snapshot/revision/load_epoch와 디스크 원본 바이트가 바뀌지 않는지 확인한다.
4. 실제 방금 저장한 구형 이력을 `adapt_verified`로 바꾸어 호환 fixture를 만든다. 이 fixture 준비는 사용자 슬롯의 자동 이관/자연 플레이로 주장하지 않는다. 모든 항목의 v2 표시가 원문과 동일한지 대조한 후 release의 실제 저장 API로 기록한다.
5. 실제 load/continue signal로 v2 저장을 다시 연다. 기존 UID/payload는 그대로 남고 새 수첩 UI는 release gate에 따라 비활성이다. 기존 모달의 읽기 전용 불변을 다시 확인한다.

한영 각각 27단언, 총 54는 위 경로의 검사 횟수다. 새로운 수첩/갤러리 UI의 release 활성화, 구형/신형 전체 저장 행렬·실패/재시도, 전편 자연 완주나 실제 마우스/키보드 입력을 검증한 것은 아니다. 헤드리스 callback을 물리 입력으로 계산하지 않는다.

## 5. Native 결과와 초기 오류

| 실행 | Native 단계 / 결과 | 사용 범위 |
| --- | --- | --- |
| build_verified | import·release export, 각각 종료 0 | 최종 production 내보내기 |
| startup_verified | 종료 0, 타이틀 bootstrap 확인 | production 일반 시작·개발 옵션 차단 |
| compatibility_build | import·release export, 각각 종료 0 | 별도 테스트 패키지 |
| probe_ko_verified | 종료 0, 27단언 PASS | 한국어 내부 호환 경로 |
| probe_en_verified | 종료 0, 27단언 PASS | 영어 내부 호환 경로 |

초기 build도 실제 receipt에서는 정상 export였지만 runner가 OrderedDictionary를 `Select-Object`로 바로 보내 요약이 null이었다. PSObject로 명시 변환하고 최종 build를 다시 실행했다. 초기 성공을 최종 5receipt에 추가해 중복 집계하지 않는다.

초기 startup은 debug 검사처럼 `--path`/`--main-pack`를 사용해 공식 release가 `compiled without support for path overrides` 오류로 종료 1을 반환했다. 제품 로직 이전의 검사 도구 오류다. 공식 release의 경로 제한을 우회하도록 엔진을 다시 컴파일하거나 사용자 설치를 변경하지 않았다. 경로 override 없는 일반 시작과 별도의 main scene을 가진 테스트 release로 정정했다. 초기 stderr/receipt는 별도로 보존하며 PASS로 바꾸지 않는다.

다음 작업 시작 시 새 TEMP 엔진 디렉터리와 이전 공식 엔진 디렉터리가 실제로 없어진 것을 확인했다. 소실 원인은 확인하지 못했다. 살아 있는 세션의 observation timeout으로 판단한 것이 아니라 Resolve-Path/Test-Path 및 디렉터리 재조회로 소실을 확인했다. 남아 있는 공식 ZIP/TPZ의 전체 SHA를 재검증하고 이 작업의 새 전용 workspace 런타임으로 복구했다. 설치된 엔진/보안 설정을 변경하지 않았다. [복구 기록](evidence/2026-10-10_release_candidate/runtime_recovery.json)에 이전/새 경로를 남긴다. 그 소실 시도는 native 프로세스를 시작하지 못했으므로 실행 성공이나 새 native 분모로 세지 않는다.

예상된 제품 경고 `GGB expects Godot 4.7.x`는 그대로 보존했다. 제품의 minor 기준을 아직 채택 전환하지 않았다는 뜻이다. foundation smoke는 release에서 unavailable이며 해당 경고가 있는 정상 타이틀 시작을 `FOUNDATION_SMOKE PASS`로 잘못 보고하지 않는다.

## 6. 도구와 독립 검사

- `godot_windows_template_policy.ps1`: 기본 debug 선택은 보존하고 `-Configuration release`일 때 정확한 release 파일만 확인한다. 다른 버전/Mono/marker 불일치/선택 템플릿 부재는 거부한다.
- 정책 fixture: PowerShell 7과 Windows PowerShell 5.1 각각 19조건 PASS. fixture의 빈 EXE는 실행하지 않으며 확인한 자기 GUID 임시 경로만 정리한다.
- `run_windows_release_candidate.ps1`: TEMP 제품/근거·새 격리 저장소·native 완료/오류/timeout·release artifact·원본 해시를 확인한다. 명시 엔진/템플릿은 읽기 전용 입력이다. 이미 있는 근거 폴더를 덮어쓰지 않는다.
- `audit_windows_release_candidate.ps1`: 확정 원본 640개와 허용된 진입 경로/fixture/UID만 대조하고 5receipt·7native 단계의 원자료와 release flag·엔진/템플릿/runner·locale·27단언·단계 목록·실제 보존 EXE/PCK를 확인한다. debug 내보내기·다른 템플릿·제품 변경·native 실패·단계 누락·바뀐 로그의 6반례를 모두 거부했다.

최종 독립 확인은 13,056개다. native 54단언·정책 각 19조건과 합산해 기능 조합 수로 만들지 않는다. [검사 결과](evidence/2026-10-10_release_candidate/checks.json)와 [원자료 폴더](evidence/2026-10-10_release_candidate/)를 참조한다.

```powershell
./scripts/audit_windows_release_candidate.ps1 `
  -EvidencePath ./ideas/md/v04/issues/validation/evidence/2026-10-10_release_candidate `
  -SelfTest
./scripts/test_godot_windows_template_policy.ps1
./scripts/validate_docs.ps1
```

보관 바이너리를 옮긴 경우 `-ArtifactRoot`에 `production`/`compatibility_test_only`를 포함하는 새 루트를 지정한다. 바이너리 부재는 무결성 검사를 통과한 것으로 취급하지 않는다. 새로운 실행은 runner의 EnginePath/ProjectPath/TemplateRoot/EvidencePath와 Mode를 명시한다. preset 이름은 기존 `Windows Desktop Debug`를 쓰지만 빌드 flag는 반드시 `--export-release`이며 receipt에서도 확인한다.

## 7. 남은 인수와 전달

T22f3a의 위 경로만 완료한다. 최신 코드의 후보 전체 기능 회귀·실제 렌더러/지원 GPU·DPI/접근성·IME 경계·마우스/키보드 전용 전편·저장 실패 행렬·정식 cold/warm 성능과 release 채택 전 계약은 남아 있다. 사용자 실제 IME 다섯 국소 정상 응답은 기존 근거이며 이번 새 물리 입력으로 집계하지 않는다. 개인 자유 메모 및 최종 아트/BGM/SFX는 이번 범위 밖이다.

ERR-0042는 OPEN, ERR-0027과 전체 목표는 IN_PROGRESS이며 제품 4.7/OFF를 유지한다. 도구/테스트/근거만 선택해 develop에 전달하고 사용자 변경 SHA·같은 Git tree의 독립/문서 검사·원격 SHA를 확인한다. 결과는 [전체 ToDo](notebook_history_TODO.md)의 별도 전달 항목에서 추적한다.

## 8. 전달 확인

develop `e5a24ba21c34c562f1934a63f6c939932d471767`에 선택 63파일을 commit하고 일반 push 후 원격 SHA 일치를 확인했다. 동일 tree `df989a3308b34a50b4945f8f5da1da1e2b7e8090` 아카이브에서도 독립 13,056확인/6반례와 실제 보존 EXE/PCK 재해시, 문서 437개/이슈 74개 검사 PASS다. 실제 개발 폴더의 문서 447개도 PASS이며 기존 사용자 변경 17개 SHA와 미추적 파일을 보존했다. 배포 바이너리나 사용자 제품 설정은 커밋하지 않았다.

T22f3a1은 위 근거 전달의 완료다. 실제 게임의 다섯 입력 조건은 기존 사용자 확인에 근거하며 새 native 자동 검사의 단언 수에 포함하지 않는다. 전체 기능/성능/전편 실제 입력과 엔진 채택은 별도로 남는다.
