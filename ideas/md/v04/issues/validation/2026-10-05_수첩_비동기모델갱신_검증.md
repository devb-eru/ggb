## 1. 변경 내용

기존 `notebook_host.refresh()`는 화면에서 사용 중인 모델을 닫고 전체 검증·구성을 동기 수행했다. 고정 저장 후보를 worker에서 준비하더라도 성공 후 이 경로에서 다시 메인 스레드를 점유했다.

| 단계 | 이번 동작 | 안전 경계 |
| --- | --- | --- |
| 요청 | 메인 스레드에서 현재 snapshot, scope, revision, 언어, 조사 문맥·필터 캡처 | 게임과 분리된 깊은 복사 snapshot만 전달 |
| 준비 | 새 RefCounted 모델에서 기존 전체 검증·공개 행 구성·필터 항목·순서 준비 | 활성 GameState·Control·SceneTree에 접근하지 않음. 본문 렌더링·레거시 저장소 생성은 UI 측 유지 |
| 대기 | 기존 자료 열람·검색·이동 유지, 고정 변경 제한 | 한 호스트당 작업 하나. 재요청은 최신 상태의 후속 요청 하나로 합침 |
| 채택 | 종료한 Thread를 join하고 scope·게임 revision·언어를 다시 확인 | 다른 슬롯·세션·로드 세대·프로필의 결과를 설치하지 않음. 언어 변경은 새 후보로 다시 준비 |
| 화면 교체 | 완료 순간의 열람 위치로 새 모델 연결, 이후 이전 모델 폐기 | 준비 중 사용자가 이동한 위치 유지. 교체 모델의 세대 키를 증가시켜 이전 키 거부 |
| 실패/종료 | 실패는 기존 화면 유지·재시도 제공. 닫기/호스트 제거는 준비 작업 정리 후 폐기 | 읽기 갱신은 저장된 게임을 쓰지 않음. 저장 성공과 화면 갱신 실패를 혼동하지 않음 |

첫 진입의 `begin()`은 이번에 비동기로 바꾸지 않았다. 스레드 종료를 강제 중단하지 않으므로 닫기/제거 시 join 대기가 발생할 수 있다. 후보와 이전 모델이 동시에 존재하는 동안 추가 메모리를 사용한다. 50회 열기/닫기 및 프로세스 RAM 인수는 별도다.

## 3. 실행 검증

| 상황 | 확인한 결과 |
| --- | --- |
| 정상 갱신 | 기존 모델로 계속 열람, 완료 후 교체, 이전 모델 키 거부 |
| 준비 중 이동 | 요청 시점이 아닌 완료 시점의 선택·분류 보존 |
| 반복 요청 | 동시 worker 증식 없이 후속 갱신 처리 |
| 언어 변경 | 이전 언어 후보 폐기 후 현재 언어 모델 적용 |
| 다른 revision | 후보 폐기, 기존 화면 유지, 명시 재시도로 최신 revision 채택 |
| reload / 슬롯 / 세션 / 프로필 변경 | 오래된 후보 미설치·회수 |
| 닫기 / 강제 호스트 제거 | 작업 join·후보 회수, 실제 저장 비변경 |
| 대용량 | 준비 중 프레임 진행, 동기 모델과 모든 공개 행의 hash 일치 |

검사는 실제 게임 controller·호스트를 사용하지만 **headless Control 호출**이다. 실제 Windows 입력·사용자 체감·OS 강제 종료 검증으로 간주하지 않는다. Thread 생성 실패 자체의 강제 주입은 하지 않았다.

| 최종 실행 | 결과 | 전체 러너 소요 |
| --- | --- | --- |
| import / export | PASS | 42.9초 / 12.7초 |
| query 및 하위 회귀 | PASS, 주 검사 4,246개 | 153.6초 |
| host 및 비동기 저장 | PASS, host 494개 / 저장 269개 | 188.4초 |

query 하위 공개 metadata 검사 64,420개, 필터/검색/원문·보존/시각 자료/갤러리 등의 결과는 원자료에 별도로 보존했다. 서로 다른 집합의 수치를 전체 요구사항 완료율로 합산하지 않는다. 모든 실행은 종료 코드 0 및 필수 PASS를 확인했다. Windows 루트 인증서 저장소 읽기 경고는 있었으며 SCRIPT/파싱/리소스 오류는 없었다.

## 4. 탐색 계측과 한계

C3 controller snapshot에 고정 `NB-PERF-L10000` archive·ledger를 넣었다. fixture는 이전 기록 10,000개 + 일반 2,000개 + 보호 6개, 5,434,278 bytes이며 SHA-256은 `cb640d6a7d1956b796f09a9c8b8be6b7758f2e098b4c71841474e47560c624a8`다. C3의 기존 수첩 정보도 전달하므로 전체 controller snapshot의 hash와 fixture hash를 혼동하지 않는다.

| 항목 | 최종 단일 headless 표본 |
| --- | --- |
| 같은 입력의 동기 모델 구성만 | 1532.048ms |
| 비동기 갱신 시작 | 394.786ms |
| 준비 중 경과 프레임 | 195 |
| 준비 대기 중 최대 관측 프레임 간격 | 119.388ms |
| 완료 검사·UI 교체 dispatch | 1068.756ms |

모델 준비가 한 번의 동기 작업으로 화면을 독점하지 않는 점은 확인했다. 그러나 시작 snapshot 복제, 완료 scope 재확인, 공개 행의 실제 Control 구성 등은 메인 스레드에 남는다. **약 1.07초의 완료 dispatch와 약 119ms의 관측 프레임 간격은 미해결 지연**이다. 단일 표본이므로 p95나 향상률을 제시하지 않는다. 동기 모델 구성 시간은 이전 전체 갱신 시간과도 다르다.

초기 탐색 빌드도 query/host PASS였지만 필터 선행 준비 전이며, 갱신 중 다른 분류로 이동했다. 시작 580.228ms / dispatch 1464.196ms / 151프레임이었고 최종 표본과 동등한 A/B 조건이 아니다. 이 값을 최종 성능 개선율 계산에 사용하지 않는다. 최종 대용량 표본은 같은 분류 안에서 선택을 바꾸며, 다른 분류 이동은 별도 정상 갱신 검사에 남겼다.
