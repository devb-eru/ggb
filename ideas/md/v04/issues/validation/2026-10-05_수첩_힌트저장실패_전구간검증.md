## 확대 범위

| 구분 | 조합 | 확인 내용 |
| --- | --- | --- |
| 저장 거부·재시도 | 15개 노드 × H1~H5 × 한영 = 150 | 최초 기록 거부, 계속 버튼 재시도 거부, 저장 복구, 동일 토큰 1회 커밋, 실제 reload |
| BF 도움 제안 | 실패 횟수 0/1/2/3/4/7(active), 2/4(resolved) × 한영 = 16 | 미대상은 창/기록 없음, 대상은 H3/H4/H5 및 상한 H5, 미요청 단계 무공개 |
| 기존 표시 분기 회귀 | 150 | 실제 표시 원문·노드·버전·언어와 카탈로그 대응 |
| 기존 과거 원문 회귀 | 24 | 과거 의미 버전별 한영 재열람·원본 불변 |

노드는 B3_A/B3_B/BF, C3/C4/CF, D0_A/D1/DF/D4, F0_A~F0_E다. H2 이상은 이전 힌트를 실제 버튼으로 읽어 정상 메뉴에 도달한 뒤 목표 힌트 저장만 실패시킨다. 재시도 뒤에도 최초 표시 토큰, 콘텐츠 의미 버전, 실제 노드/언어를 유지하며 추가 기록은 하나뿐이다. 실제 SaveManager와 LoadCoordinator로 커밋 snapshot의 동일성을 검증한다.

BF 추가 안내는 실제 구현에서 BF에만 존재한다. 다른 노드에 존재하지 않는 안내창을 추가하지 않았다. 실패 횟수 2는 H3, 3은 H4, 4와 7은 H5를 제안하고, 0/1 또는 resolved 상태는 제안하지 않는다. 제안만으로는 기록되지 않으며 실제 요청한 단계 하나만 기록한다. 핀 복구, 퍼즐 입력·관계 변경, 건너뛴 힌트의 자동 획득이 없고 H5 뒤 안내도 모든 앞 단계를 읽었다고 주장하지 않는다.

## 선행 검사 실패와 수정

1. 최초 확장에서는 H2~H5 메뉴를 이전 관찰 없이 직접 열어 120개 fixture가 본문 표시 전에 차단됐다. 메뉴 복귀 상태는 이전 힌트의 관찰 근거를 요구한다. 검사를 실제 UI 순서로 수정했으며 이 보호 규칙을 완화하지 않았다.
2. 다음 실행은 150개 복구와 16개 제안 조건을 수행했지만, 안내창이 열린 상태에서 배경 조사 flush를 허용해야 한다는 검사 단언 150개가 실패했다. `_flush_notebook_surfaces`는 상호작용 차단 중 거부하는 것이 정상이다. 기초 화면 기록 확인을 창을 열기 전으로 옮겼다.
3. 최종 실행에서 150개 복구·16개 지원 case의 ok가 모두 true, 전체 errors가 비었음을 확인했다. 선행 실패를 통과로 계산하지 않았다.
