# 저장 헤더 교체와 단일 본문 직렬화 검증

## 기준과 구현

- 기준 develop `3dcb53808648bd90961238f1adc93a3f5bd011bd`.
- [저장 구간 프로파일](2026-10-06_수첩저장_구간프로파일.md)에서 큰 `encode_payload` 비용을 확인했다. 기존 함수는 canonical payload를 만들고 checksum 없는 전체 JSON과 checksum 있는 전체 JSON을 각각 직렬화했다.
- checksum 없는 전체 JSON은 한 번 만들고 기존 방식으로 서명한다. JSON API로 직렬화한 헤더 접두부가 그 전체 JSON의 시작과 정확히 같을 때에만 서명된 헤더로 교체하고 본문 suffix를 그대로 사용한다.
- 중첩 `checksum`이나 본문 문자열을 검색·치환하지 않는다. 헤더의 JSON 문자열 개행 escape와 실제 indentation을 구분한다.
- 접두부가 맞지 않으면 기존 전체 JSON 직렬화로 fallback한다. schema·checksum 알고리즘·canonical 키 순서·영속 성공/복구 절차는 변경하지 않는다.

## 검증 범위

- 작은 본문 5종 × 헤더 5종 + 실제 대용량 fixture 4종 = 29조건. 일반/구형 schema, 중첩 checksum, checksum 같은 문자열·한국어·개행/탭/역슬래시, 누락 checksum, 빈 헤더/본문과 큰 기록을 포함한다.
- 직전 이중 전체 직렬화 구현과 최종 UTF-8 바이트/서명이 같고 호출자 입력이 불변인지 검사한다. 모든 정상 fixture가 실제 fast path 접두부를 만족하는지 확인한다.
- 접두부 불일치를 강제한 테스트 subclass에서도 기존 전체 인코더와 바이트가 같아야 한다. 빠른 경로만 통과하고 fallback을 미검증으로 두지 않는다.
- 이관·미래 버전·손상 checksum·백업·승격 실패 및 실제 수첩 host/worker 저장 회귀를 실행한다.
- 같은 고정 입력의 수정 전/후 PCK에서 네 fixture·한영 실제 저장 구간을 계측한다. 바이트 동일성과 실행 결과 확인 전 완료 처리하지 않는다.

## 남은 사항

읽기/검증·후보 준비·전체 UI 성능/실제 입력·장비별 cold 20/warm 100과 전체 생산자 인수는 남는다. 이번 변경으로 전체 저장이 비동기화된 것은 아니며 기본 rollout 비활성을 유지한다.
