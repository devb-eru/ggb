## 3. 각 경로에서 확인한 계약

1. 실제 controller의 선택창을 열어 질문을 저장한다.
2. HISTORY 저장은 허용하고 게임 저장만 거절한다. 거절 횟수가 정확히 1인지 검사해 단순 UI 차단을 저장 실패로 오인하지 않는다.
3. 선택 답변 하나는 남지만 커서는 `selection_pending`이며 물리·관계·실패 횟수·지식은 바뀌지 않는다.
4. 관찰 추가와 그 관찰로 뒷받침된 화면 receipt만 허용하는 기존 비교기를 쓴다. 세정제를 임의 소비한 변조는 비교기가 거부한다.
5. 실제 테스트 슬롯에서 load하고 controller를 제거·재생성한다. 자동 기믹 실행이나 기록 추가 없이 같은 선택 토큰을 복원한다.
6. 재시도는 저장 성공 응답 유실도 복구하면서 정확한 효과를 적용한다.
7. 순찰 대응은 세정제를 소비하지 않는다. 건식 검사는 실제 경로의 진단값과 결과 선택창을 만들고 물리적 실패를 발생시키지 않는다.
8. 젖은 흔적은 세정제를 소비하고, 정상이면 표면을 열고 오류면 잠근다. 오류 횟수는 1회만 증가하며 도구 회수는 `tool_confiscated`로 구별한다.
9. 취소는 저장된 시도 답변을 지우지 않으며 기믹을 실행하지 않는다. 과거 답변과 실제 성공은 별개다.
10. 재시도/취소 후 원래 답변은 중복·변조되지 않는다. 오래된 선택 callback은 다시 실행되지 않는다.

## 5. 초기 검사 실패와 수정

최초 신규 fixture는 이미 열린 controller에 checkpoint 상태만 설치하고 정상 `session.initialize()`를 거치지 않았다. 재생성 시 기본 세션 상태가 추가되어 커서의 게임 상태 기준이 달라졌고 복귀 검사가 실패했다. 후속 단언도 실패했으며 없는 C4 실패 기록에 직접 접근해 테스트 스크립트가 중단되었다.

선택창을 열기 전에 정상 세션 초기화를 거치도록 fixture를 수정했다. 실패 기록이 없을 때는 안전하게 실패 단언을 출력하도록 변경했다. 그 뒤 32경로가 통과했고 저장 거절 횟수 단언을 추가한 최종 빌드도 다시 통과했다. 초기 실패를 제품의 데이터 손상으로 보고하지 않는다.

## 6. 남은 범위

- 이 실행은 같은 프로세스의 실제 디스크 load + controller 재생성이다. 거울의 별도 OS 프로세스 종료/재시작 검증은 아니다.
- 실제 Windows 마우스/키보드/IME 입력이 아닌 선택 처리 메서드 호출이다.
- NP05 현장 수첩 페이지의 조건별 표시·실패 경로, NP07 overlay 등 다른 생산자 선택창의 전체 감사는 남아 있다.
- 모달 표시/선택 기록 자체의 모든 실패 조합, 퍼즐의 모든 잘못된 경로, 모든 관계/경계 조합을 전수 검증한 것은 아니다.
- 전 구간 실제 완주와 성능 인수는 전체 ToDo에서 계속 관리한다.
