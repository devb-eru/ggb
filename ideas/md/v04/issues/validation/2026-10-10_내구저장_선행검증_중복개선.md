## 변경과 신뢰 경계

기존 `save_snapshot`은 매 대사 저장마다 변경하지 않은 main/bak도 전체 JSON 파싱·정규화·원장 검증했다. 새 임시 파일의 전체 검증에서 확보한 소형 인증 메타를 다음 저장의 **선행 검사만** 재사용한다.

| 경계 | 규칙 |
| --- | --- |
| 허용 대상 | debug v2 rollout의 기본 SaveManager 인스턴스, 전체 검증한 schema 2 바이트만 |
| 키 | 저장 root, build flavor, rollout, 실제 전체 파일 바이트의 SHA-256 |
| 저장 내용 | `ok`, 분리 복사한 header, `source_schema_version`만. 본문·snapshot·원본 버퍼 없음 |
| 상한 | 최대 8개, 항목당 JSON UTF-8 4,096바이트. 큰 header는 저장하지 않음 |
| main/bak 매 호출 | 파일을 실제로 다시 읽고 전체 바이트 SHA를 계산. mtime·길이·파일 안의 checksum만으로 신뢰하지 않음 |
| 캐시 미스·손상·미래 데이터·삭제 | 기존 전체 reader로 돌아가 동일한 검증·오류·복구 정책 사용 |
| 구형 schema 1 | 전체 reader 및 이관 전 원본 백업 유지 |
| 새 snapshot/임시 파일 | 기존 snapshot 준비와 새 임시 파일의 전체 재읽기·검증 유지 |
| 로드·확정 응답 복구 | `_read_and_validate`를 그대로 호출. 인증 메타를 snapshot으로 사용하지 않음 |
| 사용자 정의 저장소/하위 클래스 | 캐시 비활성. virtual reader/validator 및 실패 주입 동작을 우회하지 않음 |
| 메모리/디스크 확정 | 기존 원자 승격·정상 백업 보존·실패 복구·lost ACK 대조 계약 유지 |

인증 메타는 영속 성공을 증명하는 영수증이 아니다. 준비한 snapshot을 미리 성공 처리하거나 디스크 커밋을 생략하지 않는다. root/flavor가 달라진 메타는 사용하지 않는다. 프로세스/SaveManager 수명 밖으로 인증 메타를 직렬화하지 않는다.

검사 범위: 같은 바이트의 main/bak 인증 메타, 반환 header의 caller 변경 격리, 전체 로드, 동일 길이 checksum 손상, schema/design/cursor/knowledge/archive 미래 자료 교체, 미래 임시 파일, root/flavor 변경, 사용자 정의 저장소, 승격 실패 복원, 개수/항목 바이트 상한, schema 1 원본 백업, 삭제 후 기존 오류. 실패한 데이터를 성공 메타로 캐시하지 않는다.

## 탐색 측정

같은 수정 코드에서 `Uncached` 대조 클래스만 인증 메타를 비활성화했다. 원래 전체 선행 reader 경로를 유지하는 대조이지 수정 전 실행 파일 자체의 재측정은 아니다. 양쪽은 같은 고정 fixture를 사용하며 root/slot은 격리했다. 최초 두 저장으로 main/bak를 준비한 뒤 순서를 번갈아 각 3회 측정했다. 시간에는 실제 저장 시작부터 내구 성공 반환까지 포함된다.

| 부하/언어 | 전체 선행 검증 평균 ms | 인증 메타 평균 ms | 인증 메타 최대 ms |
| --- | ---: | ---: | ---: |
| N2000 / ko_KR | 833.17 | 532.75 | 573.21 |
| N2000 / en_US | 849.33 | 535.64 | 634.12 |
| L10000 / ko_KR | 2,572.09 | 1,472.38 | 1,516.01 |
| L10000 / en_US | 2,704.40 | 1,640.72 | 1,812.38 |
| P2001 / ko_KR | 1,664.85 | 941.48 | 963.40 |
| P2001 / en_US | 1,670.84 | 931.69 | 976.19 |
| LONG / ko_KR | 831.89 | 467.78 | 495.16 |
| LONG / en_US | 887.71 | 533.09 | 591.53 |

이는 **HEADLESS 소규모 warm 대조, 각 n=3**이다. cold 20/warm 100·장비 계층·GPU·실제 host 입력 프레임 인수가 아니며 정식 p95를 주장하지 않는다. 모든 부하에서 이번 평균은 줄었으나 L10000·P2001은 여전히 750ms를 넘고 전체 동기 저장의 UI 차단은 남는다. 낮은 표본으로 합격이나 보장 개선율을 선언하지 않는다.

기존 `notebook_performance_probe.gd::TimedSave`는 사용자 정의 저장소이므로 의도적으로 인증 메타가 비활성이다. 이후 활성 경로의 정식 반복 측정은 기본 저장소 호출을 감싸는 계측기로 해야 한다. 기존 T24a를 새 최적화의 측정으로 재사용하지 않는다.

## 실패 원자료와 재현

첫 집중 스크립트는 `ProjectSettings.get_setting`의 Variant 타입 추론 경고가 오류로 처리돼 로드하지 못했다. 이번에 생성한 격리 PID 22036만 실행 파일·프로젝트·검사 경로를 확인해 종료했다. 이 실행은 PASS/측정에 포함하지 않고 원 stdout/stderr·receipt와 초기 스크립트를 보관한다. `Variant` 명시 뒤 최종 검사 PID 38040에서 217확인/48표본을 얻었다. 제품 코드 import는 처음부터 native 0이었다.

원자료: [evidence](evidence/2026-10-10_save_preflight/manifest.json), [고정 소스](evidence/2026-10-10_save_preflight/source.json), [최종 집중 결과](evidence/2026-10-10_save_preflight/focused-fixed/focused.result.json). 각 원자료 바이트·SHA와 native 종료/코드 지문, 48표본의 독립 분모·native stdout/파생 결과 일치를 별도로 확인한다.

독립 검사 1,768확인/6반례 PASS. 원자료 17개의 바이트·SHA와 세 최종 실행의 264제품 스크립트/실행기/집중 스크립트 지문, stdout/stderr 영수증·원 native 결과/파생 결과 동일성을 확인했다. 반례는 원자료 누락·바이트 변경·native 실패·표본 누락·반복 ID 중복·대조 입력 불일치이며, 상위 검사를 시험하는 네 반례에서는 manifest/receipt도 함께 갱신해 단순 해시 오류만으로 거부한 것이 아님을 확인했다. 최초 실패 실행은 최종 세 실행 분모에서 제외했다.
