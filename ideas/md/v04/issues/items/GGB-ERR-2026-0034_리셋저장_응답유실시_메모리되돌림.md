## 원인과 재현

ResetCoordinator는 저장 요청이 실패로 반환되면 디스크에 같은 트랜잭션이 이미 저장됐는지 확인하지 않고 메모리 상태를 직전 단계로 되돌렸다. 실제 쓰기는 성공했지만 응답만 유실된 경우 디스크는 다음 단계이고 메모리는 이전 단계가 된다.

D6 침실/캡슐 선택 이후 리셋 저장에서 실제 SaveManager에 쓰기를 맡긴 뒤 실패 응답을 반환하는 fault injection으로 재현했다. 한영 네 재시도 경로가 E1 진입과 새 아침/기상 기록 단언에 실패했다. 데이터 손실 자체를 관찰한 것은 아니며 저장 성공과 UI/메모리의 실패 판단 불일치가 확인된 오류다. 같은 공통 코드가 정상 리셋에도 사용된다.

## 수정

저장 실패 시 기존 SaveManager.confirm_snapshot_commit으로 동일 슬롯·트랜잭션을 확인하고, 확인된 snapshot이 현재 후보와 정확히 같은 영속 값인지 비교한다. 둘 다 충족할 때만 이미 커밋된 단계로 인정해 계속 진행한다.

실제 미저장 또는 다른 snapshot의 확인 응답은 기존대로 실패 반환·메모리 rollback한다. 확인 API가 없는 저장 구현에도 기존 실패 경로를 유지한다. 정상/파열 리셋 규칙·보존 정책·schema·수첩 rollout은 변경하지 않았다.

## 검증

- 침실/캡슐 × 재시도/취소 × 한영 8경로: 경로 선택 실패 후 디스크 복귀, 타이머 끝 리셋 실패와 재시도, 응답 유실 후 정확히 한 번 E1 진입.
- 정상/파열 × 8단계 응답 유실 16개: 정확히 한 단계에서 실패 응답을 주입하고 동일 트랜잭션을 확인, 최종 idle·하루 증가 1회·영구 진행 유지·메모리/디스크 일치.
- 정상/파열 각각 첫 단계의 실제 미저장·다른 snapshot 확인 응답 4개: 거부 및 메모리 상태 불변.
- 기존 foundation 런타임 회귀와 파열 수첩 suite PASS. 실제 Windows 입력·전원 차단 실험·전체 성능 인수를 의미하지 않는다.
