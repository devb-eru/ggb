## 2. 결론

GGB의 기획 기준선은 강하다. 특히 다음 부분은 제작에 사용할 수 있을 정도로 구체적이다.

- D5 전후 수면·리셋 수명 주기.
- 사용인이 이전 루프를 기억하면서도 메인 퍼즐을 영구 차단하지 못하는 제약.
- 색, 문양, 선, 라벨, 감각 자막을 병행하는 퍼즐 정보 전달.
- 관계 완료 여부가 필수 사실과 두 엔딩을 막지 않는 구조.
- 현실·잔류 선택의 시각·입력 편향 방지.
- 상태 writer, 원자 커밋, 복구와 migration에 대한 문서 계약.

현재 가장 큰 위험은 기획의 빈칸보다 **제작 전환의 빈칸**이다. v0.4 본문은 약 31,866줄이고 schema·QA까지 상세하지만, Godot에는 연습용 씬 1개와 GDScript 5개만 있다. 검토 당시에는 2026-11-20에 2장 공개 데모와 전편 콘텐츠 완료를 동시에 요구하면서 그 사이의 기술 기반선, 버티컬 슬라이스, 챕터 알파, 현지화 락과 콘텐츠 락이 없었다. 후속 조치로 이 일정은 독립 게이트로 분리했지만 실제 인력 입력과 구현 증거는 아직 없다.

따라서 다음 문서를 더 상세화하기보다, 제품 계약 충돌을 먼저 닫고 20~30분짜리 제작 버티컬 슬라이스로 기획 가정을 검증해야 한다.

총 32개 발견을 기록했다. 현재 문서만으로 교정할 수 있는 항목은 반영했으며, 열린 위험은 결함을 방치한 상태가 아니라 팀 입력·실제 콘텐츠·구현·Windows/Steam 실기 증거가 있어야만 닫을 수 있는 게이트로 남겨 두었다.

## 4. P1 발견 사항

### GGB-REV-2026-0001: 구현 마일스톤이 없는 11월 이중 완료선

**근거**

- `docs/milestones.md:11-12`는 2026-11-20에 2장 공개 데모와 전편 콘텐츠 완료를 동시에 둔다.
- `docs/milestones.md:44-51`은 결과물 분리만 정의하고 제작 중간 관문은 두지 않는다.
- `docs/next_work_plan.md:43-93`은 운영 자동화와 Steam 준비만 다루며 게임 구현 작업은 없다.
- `game/`에는 비어 있지 않은 `.tscn` 1개, `.gd` 5개, `.tres`·런타임 JSON 0개만 있다.

**영향**

공개 품질 데모, 전체 콘텐츠, 한·영, 저장, 접근성, Steam 빌드가 한 날짜에 처음 만난다. 일정 지연을 발견하는 시점이 너무 늦고, 데모 품질을 지키려면 전편이 함께 밀릴 가능성이 높다.

**권장 해결안**

1. `TECH_FOUNDATION`, `VERTICAL_SLICE`, `CH1_ALPHA`, `DEMO_FEATURE_COMPLETE`, `DEMO_CONTENT_LOCK`, `LOCALIZATION_LOCK`, `FULL_ALPHA`, `RC`를 독립 마일스톤으로 추가한다.
2. 11월 20일은 하나의 결과물만 주요 게이트로 둔다. 권장은 공개 데모 콘텐츠 락이며, 전편은 `FULL_ALPHA`로 별도 재산정한다.
3. 각 마일스톤에 실행 빌드, 계측 결과, 지원 언어, 임시 자산 비율, 차단 결함 기준을 둔다.

**완료 조건**

- 구현 WBS와 역할별 공수가 등록됨.
- 버티컬 슬라이스의 시작·종료 이벤트와 수용 기준이 확정됨.
- 데모와 전편의 완료일이 같은 자원을 놓고 경쟁하지 않음.

### GGB-REV-2026-0002: 제품 문서와 v0.4 접근성 계약 충돌

**근거**

- `docs/demo_definition.md:24-28`은 해상도 선택을 선택 기능, 마우스를 주 입력, 일부 키보드를 보조 입력, 대화 기록만 필수 접근성으로 둔다.
- `docs/full_game_definition.md:23-27`도 같은 축소 범위를 사용한다.
- `docs/godot_conventions.md:135-140`, `ideas/md/v04/16_색상연출_UI_접근성규칙.md:608-673`, `ideas/md/v04/18_GGB_게임기획서_v0.4_통합본.md:390-405`는 1280x720, UI·글자 200%, 키보드 전용 완주, 마우스 전용 완주, 포커스 복원과 다중 감각 대체를 필수로 둔다.

**영향**

개발·QA·Steam 상점 중 어느 문서를 따르면 되는지에 따라 완료 범위가 크게 달라진다. 특히 키보드 전용과 200% UI는 후반에 붙이기 어려운 구조 요구사항이다.

**권장 해결안**

v0.4 접근성 계약을 제품 기준으로 승격한다. `demo_definition`과 `full_game_definition`에 최소 레이아웃, 입력 동등성, 색·음향·모션 대체, 포커스 상실 정책을 동일하게 반영한다. 범위를 줄이려면 조용히 축소하지 않고 새 `GGB-DEC`로 비용과 제외 근거를 남긴다.

### GGB-REV-2026-0003: 데모 종료점·빌드 경계·정식판 승계가 하나의 계약으로 연결되지 않음

**근거**

- `docs/demo_definition.md:11,55,59`는 종료점을 단순히 `2장 종료`로만 적는다.
- `ideas/md/v04/18_GGB_게임기획서_v0.4_통합본.md:199-214`에서 2장은 D4까지이고 D5는 3장의 첫 사건이다.
- D5가 고딕 표면 붕괴라는 핵심 상품 장면이지만, 데모에서 D4 직후 끊는지 D5를 스팅어로 보여 주는지 정해지지 않았다.
- `docs/demo_definition.md:42-47`은 데모 저장 승계를 요구하지만 별도 AppID에서 정식판 `user://`를 찾고 가져오는 절차가 없다.
- `game/export_presets.cfg`, demo/full build flavor, 허용 event set이 없다.

**영향**

데모가 어색하게 끝나거나 3장 콘텐츠를 의도치 않게 포함할 수 있다. 별도 AppID·다른 앱 이름을 사용하면 저장 승계가 자동으로 되지 않을 수 있으며, 현재 `config/name="임시"`는 사용자 데이터 경로 자체를 불안정하게 만든다.

**권장 해결안**

1. 권장 종료는 `D4 완료 → D5 위장 필터 해제 스팅어 → SAVE_D5_COMPLETE → 데모 전용 종료 화면`이다. D5는 플레이 가능한 3장으로 세지 않고 데모 에필로그로 명시한다.
2. `BuildFlavor = demo | full`과 flavor별 시작·종료·허용 event registry를 정의한다.
3. 데모 종료 저장에는 `content_boundary_id=SAVE_D5_COMPLETE`, 제품 버전, build flavor를 기록한다.

실제 계약 문구는 프로젝트 계약 주체와 관할 법률에 맞춰 별도 검토한다. 운영상으로는 `RIGHTS-YYYY-NNNN` 증거 ID, 기여 범위, 외부 재료, 생성형 도구 고지, 비공개 서명 기록 참조와 검토 상태를 두고 `VERIFIED` 전에는 배포 후보로 승인하지 않는다. 기존 연습 PNG는 재사용 전에 새 canonical ID로 접수하거나 교체한다. 개인정보와 서명 원문은 공개 저장소에 넣지 않는다.

### GGB-REV-2026-0032: 확정 엔진인 Godot의 재배포 라이선스 항목이 레지스트리에 없음

**근거**

- 프로젝트는 Godot 4.x export를 전제로 하지만 `third_party_credits.csv`에는 내부 제작물 한 행만 있었다.
- Godot 공식 라이선스는 게임의 독자적 라이선스를 허용하지만, 엔진 바이너리 재배포 시 Godot 저작권 고지와 MIT 라이선스 문구를 포함하도록 요구한다.

**영향**

콘텐츠 에셋 권리만 확인하고 엔진·export template의 고지를 빠뜨릴 수 있다. 실제 Godot 빌드에 포함된 제3자 구성요소는 선택한 버전과 export template에 따라 최종 확인이 필요하다.

**권장 해결안**

`GODOT_ENGINE`을 MIT 런타임 계획 항목으로 선등록하고, 실제 release export에서 엔진과 제3자 notice를 추출해 크레딧·배포 notice에 고정한다. 선등록과 회귀 검사는 완료했으며 실제 export 증거는 구현 뒤 게이트로 남긴다.

## 7. 권장 버티컬 슬라이스

### 7.1 목표

20~30분 안에 GGB의 가장 위험한 가정을 실제 빌드로 검증한다.

```text
같은 아침의 짧은 일과
→ 수첩 표시
→ 수면 NORMAL_RESET
→ 표시 유지 확인
→ B3형 비가역 조작 실패
```

정식 본편의 이벤트를 그대로 모두 제작하기보다 P/A/B 요소를 한 경로로 압축한 개발 슬라이스로 운용한다. 정답과 데이터 ID는 정본을 사용하되, 공개 데모 콘텐츠로 자동 간주하지 않는다.

## 11. 최종 판단

문서 단계에서 닫을 수 있는 핵심 위험은 닫혔다. 제품·접근성·저장·현지화 계약을 통합했고, 11월 이중 완료선을 중간 제작 게이트로 분리했으며, 서사 존재론·아버지 기억·관계 분산·콘텐츠 고지·메타 UI·에셋 BOM·제작 규격·출시 기능표를 정본화했다. 전체 감사 중 새로 발견한 저장 버전, 입력·Windows 범위, 엔딩 시간, J4 placeholder와 F2 수량 문제도 개별 ID로 교정·검증했다.

그러나 프로젝트 전체가 제작 준비 완료인 것은 아니다. 현재 상태는 **기획·제작 계약 준비 완료, 실제 생산 능력·구현·실기 검증 미완료**다. 구현을 제외하고 남은 우선순위는 다음과 같다.

1. GitHub Issue 쓰기 권한을 복구하고 `production_backlog.md`의 계획 키를 실제 작업으로 등록한다.
2. 개인별 capacity와 2026-08-14~09-04 창작 잠금 입력을 받아 잠정 일정을 다시 계산한다.
3. 실제 기여자별 권리 범위를 검토·서명하고 비공개 증거 ID를 승인 에셋에 연결한다.
4. `PB-016` 대표 에셋 배치로 역할별 처리량을 재고, `PB-017` 버티컬 슬라이스 문자열 정본으로 집필·번역 분량을 계측한다.
5. 실제 에셋이 들어오는 즉시 329행 manifest의 `TBD`, placeholder와 승인 근거를 갱신한다.
6. 구현 시작 결정 뒤에만 기술 기반선과 20~30분 버티컬 슬라이스를 착수하고, renderer·저장·접근성·플레이타임을 계측한다.

따라서 추가 장문 기획을 무조건 늘릴 필요는 없다. 팀 입력과 플레이테스트로만 결정할 수 있는 값은 현재 문서에서 의도적으로 잠정 상태로 남겨 두는 편이 정확하다.
