# 사용인 대화 시트 작성 기준안

| 항목 | 내용 |
| --- | --- |
| 작업 | GGB-WRK-2026-0055 · 로컬 문서 작성 |
| 상태 | REVIEW · 작성 기준 제안 |
| 작성 / 검토 | Codex / beru |
| 목표 마일스톤 | PROD_01_VERTICAL_SLICE |
| 기준일 | 2026-10-28 |
| 범위 | 앞으로 추가할 사용인 대화의 목록·원문·연결·조건·효과 작성 방법 |

**대화 주제 하나는 목록의 한 행, 한 번 화면에 표시할 대사는 원문의 한 행으로 관리한다.** 여러 인물과 에피소드에 같은 규칙을 사용한다. 인물마다 별도 원문 탭을 만들지 않는다.

사용자 지시에 따라 Google Sheets는 수정하지 않았다. 이 문서의 새 목록 탭·ID·예시는 작성안이며, 현재 시트나 Godot에 등록된 기능으로 간주하지 않는다.

## 1. 탭별 역할

| 탭 | 기록할 내용 | 한 행의 단위 |
| --- | --- | --- |
| `Conversation_Index` · 추가 제안 | 대화 주제, 상대 인물, 시작·완료 노드, 작업 상태 | 독립적으로 선택하고 완료할 수 있는 대화 주제 하나 |
| `09_Runtime_Master` | 실제 대사·독백·지문·선택지와 직접 이어지는 노드 | 화면에 표시하는 발화·지문·선택지 하나 |
| `10_Route_Edge_Master` | 선택지 순서, 조건별 이동, 기본 복귀 경로 | 연결 하나 |
| `11_State_Predicate` | 대화가 열리는 조건, 첫 대화/반복 및 상태 변주 판정 | 상태 판정 하나 |
| `12_State_Effect` | 대화 완료, 관계·정보 변화 등 저장할 결과 | 상태 변경 하나 |
| `14`~`17`번 View | 집필·검수용 보기 | 정본에서 생성한 표시 |

새 목록은 관리와 검색을 위한 목차다. 실행 데이터의 정본은 기존 09~12번 탭을 유지한다. 원문은 `09_Runtime_Master.ko_KR`에만 작성하며, 목록·조건·효과 탭에 대사를 복사하지 않는다. 생성된 View와 숨겨진 Legacy 탭을 원문 수정 창구로 사용하지 않는다.

## 2. 대화를 묶는 단위

- **메뉴:** 같은 상황에서 사용인에게 건넬 수 있는 여러 주제를 모은다. 인사와 대화 종료 선택지는 메뉴에 한 번만 작성한다.
- **대화 주제:** 따로 선택하고 읽음 여부를 기록할 수 있는 단위다. 에드가의 ‘뿔 장난’과 ‘아버지 질문’은 별도 주제 두 개다.
- **대사 노드:** 주제 안에서 실제로 표시되는 한 줄이다. 노드가 여러 개라고 목록 행도 여러 개로 늘리지 않는다.
- **상태 변주:** 같은 주제가 경계도·관계·진행에 따라 달라지는 경우다. 같은 주제의 변주로 관리하고, 새로운 사실이나 독립적인 목적이 있는 대화는 새 주제로 분리한다.

에드가에게 나중에 새 일화가 추가되면 기존 주제의 끝에 계속 이어 붙이지 않고 새 주제 행을 등록한다. 같은 장소·시점의 대화라면 기존 메뉴의 선택지를 추가한다. 등장 조건이나 호출 상황이 다르면 별도 메뉴를 사용한다.

09번의 물리적인 행 배치는 **기존 본편 행을 유지하고, 하단에 선택 대화 블록을 추가하는 방식**을 권장한다. 추가 영역은 `인물 → 주제 ID → 분기 → 대사` 순으로 묶는다. 게임에서 어느 시점에 재생할지는 조건과 연결로 지정한다. 일과 종료 직전에 재생할 대화라고 해서 매번 일과 종료 행 바로 위에 끼워 넣을 필요는 없다.

데이터 중간에 제목만 있는 빈 노드 행이나 병합된 설명 행을 넣지 않는다. 블록은 행 그룹·테두리·필터 보기로 구분한다. 검수할 때는 목록에서 해당 주제의 노드만 모아 읽는다.

## 3. 대화 목록의 열

목록의 입력 열과 참조 열을 구분한다. 참조 열은 원문·연결·조건 탭에서 가져오는 읽기 전용 열로 구성하는 것을 권장한다.

### 직접 입력할 열

| 열 | 작성 방법 |
| --- | --- |
| `package_id` | 해당 에피소드 패키지. 예: `CNT-EP01` |
| `conversation_id` | 주제의 고정 ID. 예: `EP01_DLG_EDGAR_001` |
| `title` | 집필용 주제명. 예: `뿔에 붙은 벌레 장난`. 게임의 선택지 문구와 구분한다. |
| `interlocutor_id` | 대화를 거는 상대. `EDGAR`, `MARA1`, `LUCA`, `IRIS`, `MARA2` |
| `conversation_type` | 목록용 분류 제안: `DAILY`, `INVESTIGATION`, `RELATIONSHIP`, `MAIN` |
| `menu_node_id` | 이 주제를 선택할 수 있는 메뉴의 시작 노드 |
| `choice_node_id` | 이 주제를 고르는 `CHOICE` 노드 |
| `entry_node_id` | 선택 후 처음 재생할 대사 노드 |
| `completion_node_ids` | 정상 완료가 성립하는 마지막 대사 노드 ID의 JSON 배열. 결말이 하나면 원소 하나 |
| `repeat_entry_node_id` | 별도 반복 반응의 시작 노드. 없으면 `NONE` |
| `integration_status` | 연결 작업 상태 제안: `NOT_CONNECTED`, `CONNECTED`, `VERIFIED` |

### 다른 탭에서 가져올 열

| 표시 열 | 가져올 위치 |
| --- | --- |
| 선택지 문구 | `choice_node_id`에 해당하는 09번 `ko_KR` |
| 등장 장소 | `entry_node_id`에 해당하는 09번 `location_id` |
| 개방 조건 | 09번 `display_condition_id`와 이에 연결된 11번 조건 |
| 반복 규칙 | 09번 `repeat_policy` |
| 복귀 대상 | 완료 노드의 09번 `next_type`·`next_id` |
| 원문 검수 상태 | 해당 주제 노드들의 09번 `approval_status`. 일부만 승인되었으면 전체 승인으로 표시하지 않는다. |

`interlocutor_id`는 목록에서 찾기 위한 상대 인물이다. 09번의 `speaker_id`·`owner_id`를 이 열로 대체하지 않는다. 주인공의 발화도 에드가와의 대화 주제에 속할 수 있다.

목록의 새 분류·연결 상태 값은 이 문서에서 제안하는 관리 값이다. 기존 Runtime의 `content_type`이나 `approval_status`에 넣지 않는다. 목록을 추가하더라도 현행 importer가 자동으로 메뉴를 생성하거나 조건을 실행하지는 않는다.

### 목록 예시

| conversation_id | title | interlocutor_id | conversation_type | menu_node_id | entry_node_id | integration_status |
| --- | --- | --- | --- | --- | --- | --- |
| `EP01_DLG_EDGAR_001` | 뿔에 붙은 벌레 장난 | EDGAR | DAILY | `EP01_MENU_EDGAR_HALL_001` | `EP01_DLG_EDGAR_001_010` | NOT_CONNECTED |
| `EP01_DLG_EDGAR_002` | 아버지의 성격에 대한 질문 | EDGAR | DAILY | `EP01_MENU_EDGAR_HALL_001` | `EP01_DLG_EDGAR_002_010` | NOT_CONNECTED |
| `EP01_DLG_MARA1_001` | 새 일화의 작성명 | MARA1 | DAILY | `EP01_MENU_MARA1_HALL_001` | `EP01_DLG_MARA1_001_010` | NOT_CONNECTED |

위 ID는 형식을 설명하는 예시다. 실제 등록 전에는 기존 ID와 중복되는지 확인한다. 다른 장소의 같은 인물을 등록할 때 기존 주제 ID를 장소에 맞춰 개명하지 않는다.

## 4. ID와 정렬

| 대상 | 새 대화의 명명 예시 |
| --- | --- |
| 주제 | `EP01_DLG_EDGAR_001` |
| 주제 안의 대사 | `EP01_DLG_EDGAR_001_010`, `_020`, `_030` |
| 주제를 고르는 선택지 | `EP01_DLG_EDGAR_001_CH01` |
| 주제의 반복 반응 | `EP01_DLG_EDGAR_001_REPEAT_010` |
| 공통 메뉴 시작 | `EP01_MENU_EDGAR_HALL_001` |
| 메뉴의 선택 연결 | `EP01_CHOICE_EDGAR_HALL` |
| 조건 | `PRED_EP01_DLG_EDGAR_001_...` |
| 효과 | `EFF_EP01_DLG_EDGAR_001_...` |

- `conversation_id`는 인물별 주제 번호이며, 마지막 숫자가 화면 표시 순서를 뜻하지 않는다.
- 새 주제는 새 ID를 받는다. 행 삽입·정렬·집필 순서 변경으로 기존 ID를 다시 매기지 않는다.
- 대사 삽입은 새 노드 ID를 발급한 뒤 `order`와 `next_id`를 고친다. 기존 노드의 ID는 유지한다.
- 같은 장면의 주제는 기존 `scene_id` 안에 묶는다. 일상 주제를 추가할 때마다 본편 Scene 번호를 새로 소비하지 않는다.
- `draft_id`, 제작 묶음 `content_item_id`, 승인 후 `line_id`는 기존 발급 계약을 따른다. 목록의 `conversation_id`와 같은 필드로 취급하지 않는다.
- 미발급 ID는 해당 열의 기존 규칙에 따라 `NONE`으로 쓴다. 승인되지 않은 대사에 정식 `line_id`를 임의로 만들지 않는다.

실행 연결에는 행 번호나 ‘바로 다음 줄’을 쓰지 않는다. 2026-10-28 조회에서 기존 `EP01_AS_002`는 147행에서 149행으로 이동해 있었다. 연결 기준은 계속 `EP01_AS_002`다.

## 5. 09번 원문 작성

| 상황 | 행 작성 |
| --- | --- |
| 사용인의 대사 | `DIALOGUE`, 실제 `speaker_id`, 발화 본문만 `ko_KR`에 기록 |
| 주인공의 말 | `DIALOGUE`, `SUBJECT` |
| 주인공의 속생각 | `MONOLOGUE`, `SUBJECT` |
| 플레이어가 읽을 지문 | 별도 `CAPTION` 행, `SYSTEM` |
| 선택지 | 선택지마다 별도 `CHOICE` 행, 선택지 문구만 기록 |
| 제작 지시 | `direction`에 기록. 플레이어에게 보여 줄 지문과 구분 |

한 행에 `에드가: … / 나: … / 지문: …`를 함께 적지 않는다. 화자가 바뀌면 행을 나눈다. 한 화자가 이어서 말하더라도 화면 표시를 나눌 필요가 있으면 별도 노드를 사용한다.

`speaker_id`와 `character_art`는 독립적으로 작성한다. 주인공이 말하는 동안 에드가 초상이 표시될 수 있다. 일러스트가 없다는 이유로 화자를 `SYSTEM`으로 바꾸지 않는다.

선택지는 같은 메뉴 안에서 표현 방식을 통일한다. 예를 들어 `에드가를 조금 놀려본다 / 아버지에 관해 묻는다`처럼 행동 방향을 맞춘다. 선택지의 문구와 선택 후 실제로 말하는 문장을 각각 기록한다.

09번의 기존 38개 열을 유지한다. 이 문서의 `conversation_type`을 `content_type`에 넣거나, 목록용 열을 Runtime에 임의로 덧붙이지 않는다.

## 6. 10번 선택지와 복귀 연결

```text
공통 인사 노드
  → 선택지 route
      ├─ 주제 A의 CHOICE → A 시작 → A 마지막 대사 → 호출한 허브
      ├─ 주제 B의 CHOICE → B 시작 → B 마지막 대사 → 호출한 허브
      └─ 대화를 마친다 → 호출한 허브
```

- 선택지 하나마다 10번의 연결 한 행을 작성한다. 버튼 순서는 `edge_order`로 정한다.
- 선택형 route의 각 대상은 09번에 실제로 존재하는 `CHOICE` 노드다. 그 노드의 `next_id`가 해당 주제의 첫 대사를 가리킨다.
- 자동 조건 분기는 `router`로 분리한다. 조건 비교와 안전한 fallback을 작성하며, fallback이 다른 선택지의 답변 본문으로 들어가게 하지 않는다.
- 일반 일상 대화는 끝나면 호출한 허브로 돌아간다. 인사를 재생하는 메뉴로 무한 재진입시키지 않는다.
- 마지막 줄의 `next_type`·`next_id`를 반드시 적는다. 시트에서 바로 아래에 있는 다른 주제로 흘러가지 않게 한다.
- 표시할 주제가 하나도 없을 때도 대화 종료 경로는 남긴다.
- 대화 메뉴의 ‘대화를 마친다’와 본편의 ‘일과를 마친다’를 별도 연결로 관리한다. 일상 주제의 끝을 공통 일과 종료 노드로 일괄 연결하지 않는다.

`location_id=M1_CENTRAL_HALL`은 공간이고, 허브 ID는 실행 연결 대상이다. 공간 ID를 허브 ID 대신 넣지 않는다. 새 허브나 `SYS_RETURN_TO_PARENT` 같은 공통 복귀 기능을 사용할 때는 대상 등록과 실제 지원 여부를 확인한다.

## 7. 11번 등장 조건

조건은 ‘어디서’, ‘언제’, ‘무엇을 확인한 뒤’, ‘어떤 상태일 때’를 판정할 수 있게 작성한다.

| 작성할 판정 | 예 |
| --- | --- |
| 위치 | 중앙홀에 있을 때 |
| 진행 시점 | 개별 업무를 마치고 일과 종료를 선택하기 전 |
| 선행 내용 | 특정 대화를 완료한 뒤 |
| 관계·경계 | 이미 정의된 bond/alert 구간 |
| 반복 여부 | 이 주제를 해당 범위에서 완료했는지 |

자연어는 설명 칸에 쓰고, 실행에 필요한 판정은 등록된 `state_path`, `comparator`, `typed_value`, `value_type`로 정의한다. 09번의 `display_condition_id`와 분기 route의 `predicate_id`는 그 판정으로 연결한다.

여러 조건의 AND/OR를 쓸 경우 조합과 평가 순서를 명시하고 기술 담당자가 지원 여부를 확인한다. `notes`에 조건을 여러 줄 적거나 `logic_group` 이름만 추가한 것으로 실행 조건이 완성되었다고 보지 않는다.

현재 상태에 없는 ‘일과 종료 직전’ 같은 새 단계가 필요하면 실제 상태 계약과 런타임 연결이 먼저 필요하다. 존재하지 않는 경로에 `REGISTERED`를 붙이지 않는다. 상태 경로 미등록·조건 미연결은 목록의 `integration_status=NOT_CONNECTED`로 남기고 실행 반영을 완료로 표시하지 않는다.

## 8. 반복과 완료 기록

새 주제를 만들 때 반복 범위부터 정한다. `repeat_policy` 이름만 적고 끝내지 않고, 12번 효과의 저장 위치와 11번 재진입 조건까지 함께 작성한다.

| 의도 | 사용할 기존 값 | 함께 정할 내용 |
| --- | --- | --- |
| 해당 플레이에서 한 번만 읽음 | `once` | 영구 완료 기록과 이후 메뉴 노출 여부 |
| 루프마다 다시 열림 | `per_loop` | 루프 로컬 완료 기록과 정상 리셋 후 초기화 |
| 첫 본문 뒤 짧은 반복 반응 | `first_repeat` | 첫 읽음 기록의 유지 범위, 첫/반복 route, 반복 시작 노드 |
| 조건 구간마다 별도 최초 반응 | `per_state` | 어떤 변주를 다른 상태로 셀지와 변주별 완료 기록 |
| 관계·진행에 따라 문구가 달라짐 | `state_variant` | 조건별 대상 노드, 각 변주의 반복 처리 |
| 매번 표시 | `always` | 중복 완료·보상을 기록하지 않을 방법 |

`protected`는 프로젝트의 보존 대상 콘텐츠에만 사용하며, ‘일상 대화이므로 보존’ 같은 이유로 일괄 지정하지 않는다. 이 표는 새 대화 작성 시 결정할 항목이며 기존 노드의 반복 의미를 자동 변경하는 규칙이 아니다.

완료 기록은 목록의 `completion_node_ids`에 해당하는 마지막 대사를 끝까지 읽은 뒤 저장한다. 메뉴를 열거나 선택지를 누른 순간, 중간에 닫은 순간에는 읽음 완료를 기록하지 않는다. 종료·취소 선택지는 주제 완료에 포함하지 않는다.

첫 대화와 반복 반응이 둘 다 필요하면 09번에 별도 노드로 작성한다. 본문을 복사해 두고 나중에 줄이는 방식은 쓰지 않는다. 변주별 완료를 쓰더라도 관계 보상까지 같은 횟수로 반복 지급하지 않는다.

## 9. 12번 결과 작성

| 결과 | 기록 기준 |
| --- | --- |
| 대화를 읽음 | 주제 ID와 완료 범위로 관리 |
| 새로운 사실을 얻음 | 실제로 공개한 정보에만 정본 `knowledge_id` 사용 |
| 관계·경계 변화 | 변화가 승인된 경우에만 별도 효과 행 작성 |
| 사용인의 기억 변화 | 해당 인물이 기억을 얻는 사건으로 별도 작성 |

이 네 결과를 하나의 ‘대화 완료’ 플래그로 대신하지 않는다. 단순 일상 대화의 기본 결과는 읽음 기록이며, 정보나 관계 변화가 없으면 그 효과 행을 만들지 않는다.

각 효과에는 실제 완료 노드, 저장할 경로·연산·값, writer, commit 시점과 반복 범위를 적는다. 정상 완료 지점이 여러 개면 어느 지점에서 같은 결과가 성립하는지 모두 연결하고 중복 적용을 막는다.

기존 등록 경로인 영구 `meta_progress`와 루프 로컬 `loop_state`의 구분을 따른다. 개별 경로나 키의 사용 가능 여부는 상태 Registry와 writer 계약으로 확인한다. 대화 목록이 저장 상태를 직접 쓰는 기능은 추가하지 않는다.

## 10. 새 대화 추가 순서

1. 목록에 주제 한 행을 등록하고 ID·상대·분류·등장 상황·반복 의도를 정한다.
2. 기존 메뉴에 추가할지 새 메뉴가 필요한지 정한다.
3. 09번의 선택 대화 영역에 인사·선택지·본문·반복 반응을 작성한다. 공통 인사는 기존 메뉴를 재사용한다. 새 행은 기존 행의 서식·데이터 검증·참조 수식을 보존하며 추가한다.
4. 10번에 선택 연결, 조건 분기, 종료·복귀 경로를 작성한다.
5. 11번에 등장·선행·반복 판정을 작성하고 등록 상태를 확인한다.
6. 12번에 완료·정보·관계 효과 중 필요한 것만 작성한다.
7. 목록의 노드 참조와 참조 열을 갱신한다.
8. 생성 View를 갱신하고 원문 검수와 실행 연결 검증을 나누어 진행한다. 납품 전 09~12번 CSV를 함께 내보내 기존 schema·Vocab·상태 Registry·이전 원문 기준본으로 lint한다.

`approval_status`는 기존 값 `draft → in_review → approved`를 사용하며 반려는 `rejected`다. 글이 승인되었다는 이유만으로 실행 검증까지 끝난 것으로 표시하지 않는다. `integration_status=VERIFIED`는 실제 연결과 검증 근거를 확인한 뒤 지정한다.

새 대사는 기존 행을 삭제하거나 기존 `ko_KR`를 덮어써서 넣지 않는다. 기존 대사 개정이 필요하면 별도 개정 범위와 보존 방법을 합의한다. 승인 상태·revision·line_id 및 저장된 관찰의 과거 버전을 함께 관리한다.

## 11. 필터와 보기

기본 목록은 `에피소드 → 상대 인물 → 대화 종류 → 주제 ID` 순으로 본다. 실제 메뉴 순서와 대사 재생 순서는 각각 10번 `edge_order`, 09번의 명시적 연결로 관리한다.

인물별 새 원문 탭 대신 필터 보기를 만든다. 자주 쓸 보기는 ‘에드가’, ‘마라 1’, ‘일상 대화’, ‘미검수’, ‘미연결’, ‘반복 반응 누락’이다. 긴 기술 참조 열은 접고 주제명·인물·장소·개방 조건·반복·검수·연결 상태를 먼저 보이게 한다. 색만으로 상태를 구별하지 않는다.

## 12. 추가할 때 확인할 항목

- [ ] 목록의 한 행이 독립적으로 선택·완료할 수 있는 주제 하나인가?
- [ ] 본문은 09번에만 있고 화자·지문·선택지가 각각 분리되어 있는가?
- [ ] ID가 기존 ID와 겹치지 않고, 추가 과정에서 기존 ID와 원문을 바꾸지 않았는가?
- [ ] 선택지 문구·시작·모든 정상 완료·반복 노드가 실제로 존재하는가?
- [ ] 각 선택이 자신의 답변으로만 들어가고, 종료 뒤 다른 주제로 새지 않는가?
- [ ] 주제 없는 메뉴, 대화 종료, 중간 종료·재개 경로가 있는가?
- [ ] 등장 조건이 등록된 상태를 읽으며 fallback이 있는가?
- [ ] 첫 읽음·같은 루프 반복·다음 루프·상태 변주에서 의도대로 동작하는가?
- [ ] 완료 전에 읽음 처리하거나, 재열람으로 정보·관계 효과를 중복 적용하지 않는가?
- [ ] 대화 종료와 일과·본편 진행 완료가 분리되어 있는가?
- [ ] 원문 승인과 런타임 검증 상태가 구분되어 있는가?
