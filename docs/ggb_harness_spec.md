# GGB 맥락 복원과 선택 검증 하네스 명세

이 명세는 [운영 기획](ggb_operations_plan.md)의 1~3단계를 구현할 때 사용할 계약이다. 하네스는 AI가 작업을 수행하는 데 필요한 맥락과 명령, 검증 근거를 제공하는 얇은 실행 계층으로 정의한다. 아래 명령과 파일 구조는 구축 예정안이며 현재 실행 가능한 기능이 아니다.

## 공통 진입점

진입점은 저장소 루트에서 실행하는 `scripts/ggb.ps1`로 제안한다. PowerShell 7과 JSON을 사용하고 Godot, Node.js와 외부 연동은 기존 도구를 호출한다. 실제 엔진 경로와 개인 환경은 추적하지 않는 로컬 설정에 둔다.

| 명령 | 결과 | 주요 제약 |
| --- | --- | --- |
| `doctor` | 도구 경로와 버전, 엔진 및 템플릿 일치, LFS와 작업 트리 상태 | 비밀값 출력이나 자동 설치 없이 점검 |
| `context -Task <key>` | 작업 목표, 현재 상태, 필수 문서와 실행 근거 | 관련 시스템만 기본 포함 |
| `plan -Task <key> -Base <ref>` | 변경 파일, 영향 시스템, 검증 선택과 확대 이유 | 실행 전에 사람이 읽는 요약과 JSON 출력 |
| `check -Task <key> -Profile affected` | 고정 입력의 선택 검사와 결과 | 계획과 검사 입력이 달라지면 재계획 |
| `check -Profile integration` | 통합 후보의 검증 | 실제 병합 결과 스냅샷 기준 |
| `check -Profile full` | 등록된 전체 자동 회귀 | 수동 인수는 별도 항목으로 표시 |
| `check -Suite <id>` | 명시한 실행 단위 | 의존 준비와 추가 영향 검사를 생략한 것으로 기록하지 않음 |
| `handoff -Task <key>` | 실행 결과를 연결한 재개 요약 | 추론한 완료 상태로 Project를 갱신하지 않음 |

`context`와 `plan`은 읽기와 출력 중심으로 시작한다. 자동 수정과 외부 쓰기는 후속 단계의 별도 행동이다. 명령 출력은 짧은 결론, 선택 이유, 근거 경로 순서로 제공한다.

```powershell
# 아래는 구축 후의 사용 예시이며 현재 실행하지 않는다.
./scripts/ggb.ps1 context -Task notebook-search
./scripts/ggb.ps1 plan -Task notebook-search -Base origin/develop
./scripts/ggb.ps1 check -Task notebook-search -Profile affected
./scripts/ggb.ps1 handoff -Task notebook-search
```

## 파일 구조와 소유 정보

예정 구조는 다음과 같다. 실제 파일 수는 첫 시범에서 필요한 범위로 제한한다.

```text
AGENTS.md                              짧은 시작과 종료 안내
docs/context/project.md                현행 개발 단계와 공통 제약
docs/work_context/<task-key>/task.md    목표와 결정 및 인계 판단
scripts/ggb.ps1                        공통 진입점
scripts/ggb/systems.json               시스템과 계약 및 의존성
scripts/ggb/suites.json                실행 단위와 포함 관계
scripts/ggb/profiles.json              시점별 선택 규칙
outputs/ggb/<task-key>/<run-id>/         계획과 실행 원자료
  plan.json
  snapshot.json
  result.json
  resume.md
  logs/
```

`outputs/`는 현재 Git에서 제외된다. 실행 원자료는 이 경로에 두고, 인계 판단과 재개에 필요한 경로는 추적되는 작업 문서에 남긴다. 다른 PC에서 필요한 최종 근거는 관련 검증 문서에 선별 보관하거나 CI artifact에 연결한다. 임시 경로만 남긴 인계로 팀 사용을 완료 처리하지 않는다.

| 정보 | 정본 |
| --- | --- |
| 제품의 의도와 허용 규칙 | 현행 v0.4, 연결된 계약과 승인 결정 |
| 작업 상태와 담당 및 일정 | GitHub Project |
| 작업 목적과 완료 조건 | 연결된 Issue, 로컬 시범이면 task.md |
| 로컬 수정 범위와 미완료 판단 및 다음 행동 | task.md |
| 실제 실행 입력과 환경 및 결과 | 변경 불가능한 실행 원자료 |
| 재개용 출력 | 위 정보를 읽어 생성한 resume.md |

Issue 등록 후에는 원래 task.md의 목적과 완료 조건을 Issue로 연결해 두 곳에서 따로 변경하지 않는다. 로컬 실행 상태는 `running`, `failed`, `finished` 등 도구 내부 상태이며 Project의 `IN_PROGRESS`나 `DONE`과 같은 뜻으로 사용하지 않는다.

## 작업 계약과 인계 형식

task.md는 기존 [작업 템플릿](templates/work_item.md)의 목적과 완료 조건을 재사용한다. 여기에 AI 수행에 필요한 다음 항목을 추가한다. 작은 수정에는 필요한 항목만 적고 장시간 작업에 전체 형식을 사용한다.

```text
작업 키와 연결된 Issue
목표와 완료 조건의 정본
마지막 사용자 결정과 대체된 결정
수정할 시스템과 파일 및 공유 파일 담당
시작 branch와 HEAD 및 기존 수정의 요약
관련 계약의 경로와 절
현재 확인한 결과와 실행 근거
남은 작업과 다음 행동
추가 확인이 필요한 결정
재개할 때 먼저 볼 파일과 명령
```

재개 요약은 보통 1~2화면 안에 읽을 수 있는 크기를 목표로 한다. 프로젝트 전체 상태를 각 작업 문서에 복사하지 않는다. 새 AI는 task.md와 생성 요약을 실제 Git 상태에 대조하고 불일치를 먼저 설명한다.

예를 들어 “조회 검사 PASS, 실제 IME 인수 미완료, rollout OFF 유지”는 각각 실행 결과, 인수 조건과 제품 제약이다. 이를 “수첩 완료”로 압축하지 않는다.

## 변경 입력과 스냅샷

검증 계획은 다음 변경 집합의 합집합으로 만든다.

1. 작업 기준점과 현재 HEAD 사이의 커밋 변경.
2. 현재 index와 작업 트리의 수정 및 삭제.
3. 검사 입력에 포함할 미추적 파일.
4. task.md에 명시한 영향 시스템과 기획 계약 변경.

기준점은 PR이면 통합 대상과의 merge-base를 기본으로 하고, 로컬 연속 작업이면 작업 시작 지점을 기록한다. 다른 작업의 기존 수정도 영향 선택에서 숨기지 않는다. 자신의 수정과 기존 수정은 소유권을 구분해 표시한다.

스냅샷에는 기준 커밋, 파일 목록과 SHA-256, 누락 또는 삭제 경로, 선택한 설정, 엔진과 템플릿 지문, LFS 실제 파일 여부를 기록한다. 검증은 이 스냅샷의 복사본이나 PCK를 읽는다. 소스가 복사 중 바뀌면 지문을 다시 확인하고 그 복사본의 실행을 보류한다.

깨끗한 worktree는 기존 미커밋 수정과 미추적 에셋을 포함하지 않는다. 자동 작업의 기본 입력은 명시한 기준 커밋으로 두고, 작업 트리 내용을 포함해야 하면 파일별 반입 목록을 먼저 만든다. 다른 작성자의 수정과 개인 플러그인을 자동으로 합치지 않는다.

## 테스트 목록

모든 `.gd` 파일을 실행 가능한 테스트로 등록하지 않는다. 각 항목은 다음 필드를 가진다.

| 필드 | 의미 |
| --- | --- |
| `id`와 `kind` | 안정적인 실행 ID, CLI suite 또는 script, 포함 검사, fixture와 helper 구분 |
| `entrypoint`와 `args` | 실제 실행 명령과 필수 개발 인자 |
| `systems`와 `inputs` | 검사하는 시스템과 실제 읽는 코드 및 데이터와 설정 |
| `covers` | 같은 조건에서 함께 실행하는 하위 검사 |
| `requires` | import, fixture와 사전 준비, 독립 실행 가능 여부 |
| `variants` | locale, build flavor, rollout과 관계 경로 등 검사 조건 |
| `pass_rule` | 종료 코드와 필수 marker 및 오류 패턴 또는 구조화 결과 |
| `timeout_seconds` | 항목별 실행 제한 |
| `evidence_scope` | 함수 또는 세션 검사, 런타임 입력, 물리 입력 등 증거 범위 |
| `cost` | 마지막 실행 시간과 표본, 아직 계측 전이면 UNKNOWN |
| `ci_status` | 로컬 실행 가능 여부와 실제 CI 적용 여부 |

수첩 조회 suite의 13개 하위 검사는 현재 부모의 fixture와 tree를 사용한다. 초기에는 부모 suite로 실행한다. 단독 CLI가 없는 하위 파일에 가상의 명령을 붙이지 않는다. 실행 시간 계측에서 효과가 크다고 확인되면 fixture를 유지하는 좁은 진입점을 별도 작업으로 추가한다.

상위 suite와 하위 검사의 조건이 다르면 둘 다 실행할 수 있다. 포함 관계는 단순 파일 포함이 아니라 같은 fixture, 옵션과 locale 및 의미 범위의 포함이어야 한다.

## 시스템과 영향 선택

우선 명시적인 시스템 의존성과 경로 규칙을 사용한다. Godot의 `preload`, `load`, `class_name`, autoload, signal과 사건 ID를 통해 추가 의존 후보를 수집하지만 정적 검색 결과만으로 영향을 완전히 파악했다고 판단하지 않는다. 동적 경로와 상태 소비 관계는 사람이 확인한다.

| 변경 예시 | 초기 선택안 | 추가 조건 |
| --- | --- | --- |
| `docs/`의 일반 운영 문서 | V0 문서 검사 | 제품 계약 의미 변경이면 연결 시스템 추가 |
| `notebook_query.gd` | import, 수첩 query suite | 현재 포함된 검색과 gallery 하위 검사 중복 제외 |
| 수첩 철자 입력 또는 검색 제출만 변경 | 관련 입력과 search, query 및 호스트 연결 | 기록 생산 및 챕터 이벤트 미변경이면 생산자 전수 감사 제외 |
| `notebook_panel.gd` | query, opening 및 host 관련 suite | 화면 배치와 포커스 변경은 실제 화면 조건 추가 |
| 수첩 저장 또는 view sidecar | query의 포함 검사, migration 및 host 관련 경로 | 스키마와 복구 변경이면 저장군 및 캠페인 확대 |
| 특정 챕터의 세션 또는 controller | 해당 챕터, 해당 생산자와 저장 복귀 | 공통 상태 또는 후속 진입 영향이면 연결 챕터 추가 |
| `save_manager.gd` 또는 reset/state writer | foundation 및 저장군, 주요 소비자, full campaign | demo/full, 실패 복구와 재선택 등 위험별 variant 추가 |
| 공통 표시 및 입력 router | 관련 UI와 focus, 재설정, 호스트와 복귀 | 동작을 바꾸면 입력 경로 인수 연결 |
| 음원 또는 cue 및 asset manifest | V0, 오디오 smoke와 실제 리소스 로드 | loop와 음량 및 청취 품질은 별도 확인 |
| Discord 알림 스크립트 | Node.js 운영 테스트 | Godot 전편 검사는 선택하지 않음 |
| 엔진과 `project.godot` 및 export 설정 | import와 넓은 런타임, 영향 export | 물리 IME와 GPU 및 release 조건은 별도 선택 |

이 표는 선택안이다. 실제 실행 ID와 variant는 목록 대조 후 확정한다. `game_audio_smoke.gd` 등 파일의 존재만으로 이미 독립 실행이 가능하다고 가정하지 않는다.

선택 알고리즘은 다음 순서로 구현한다.

1. 변경 파일을 시스템에 연결하고 변경 전 경로와 삭제 경로도 포함한다.
2. 명시한 의존성의 역방향 소비자와 계약 영향을 따라 확장한다.
3. 공통 저장과 상태 또는 엔진 등 위험 규칙으로 필요한 프로필을 추가한다.
4. 등록된 suite와 variant로 변환하고 사전 준비를 붙인다.
5. 조건이 같은 `covers` 중복을 제거한다.
6. 미분류 경로, 새 테스트와 설명되지 않는 동적 의존성을 표시한다.
7. 미분류가 국소 시스템으로 제한되면 그 시스템군, 제한되지 않으면 전체 자동 회귀로 확대한다.
8. 선택 이유와 제외 이유 및 수동 확인을 plan.json에 기록한다.

검증 시간 예산은 먼저 예상 비용을 알리는 용도로 쓴다. 시간이 오래 걸린다는 이유로 필수 검사를 조용히 삭제하지 않는다. 사용자가 별도 범위를 지정하면 남은 검증을 명시적으로 인계한다.

## 검증 프로필과 전체 회귀

| 프로필 | 사용 시점 | 내용 |
| --- | --- | --- |
| `docs` | 일반 문서 수정 | 현행 V0와 관련된 참조 |
| `affected` | 개발 반복 | 변경 시스템과 연결 계약, 위험에 따른 확대 |
| `integration` | 실제 통합 브랜치에 반영할 후보 확정 | 전체 자동 회귀 확인, 영향 합집합부터 실행하고 유효 근거 재사용 |
| `full` | 정의한 통합 게이트와 마일스톤 | 등록된 모든 자동 suite와 필요한 variants |
| `acceptance` | 공개 또는 특정 인수 | 실제 입력, 화면, 성능과 청취 등 요구별 절차 |

프로필은 V0~V5와 병렬인 완료 체계가 아니다. 각 프로필 결과에 어떤 V 단계의 어느 요구를 검사했는지 표시한다. 기존 `run_godot_foundation.ps1`은 기반 회귀의 기존 묶음으로 남기고, 테스트 목록과 대조해 빠진 실행 단위를 확인한다.

사용자가 선택한 주기에 따라 통합 게이트와 마일스톤에는 전체 자동 회귀를 적용한다. 개발 중인 부분 결과를 모아볼 때는 영향 합집합을 사용하고, 실제 통합 후보 확정 시 `integration`으로 전환한다. 매 작은 수정이나 에이전트 메시지를 통합 게이트로 취급하지 않는다.

전체 자동 회귀의 범위도 먼저 명시해야 한다. “기반 스크립트 실행 완료”와 “전편 캠페인 통과”와 “모든 자동 검사 통과”는 서로 다른 주장이다. 정의한 전체 목록 밖의 수동 인수도 함께 미완료로 보여준다.

## 실행 격리와 결과 판정

각 실행에 GUID 기반 `run-id`를 발급하고 `%TEMP%/ggb-runs/<run-id>/` 안에 프로젝트 복사본과 사용자 데이터 위치를 만든다. 원자료는 `outputs/ggb/`로 선별 보관한다. 같은 실행에서도 테스트 간 fixture 공유가 명시되지 않으면 사용자 데이터 위치를 나눈다.

현재 [기반 실행기](../scripts/run_godot_foundation.ps1)의 고정 TEMP 경로와 제한 없는 대기를 공통 실행 계약으로 바꾼다. 변경 전에는 이 실행기를 병렬 호출하지 않는다. [실행 감사](../scripts/run_notebook_runtime_audit.ps1)와 [성능 계측](../scripts/measure_notebook_performance.ps1)의 기존 격리와 receipt 처리를 재사용한다.

엔진의 실제 `user://` 경로가 격리 루트 안인지 검사한다. APPDATA 설정만으로 격리를 확정하지 않고 portable 모드와 프로젝트의 사용자 경로 설정도 확인한다. 일반 슬롯, 개발 슬롯과 profile이 검사 외부 위치를 쓰면 실행을 실패 처리한다.

PASS는 다음 조건을 모두 요구한다.

- 프로세스가 제한 시간 안에 정상 완료했다.
- 종료 코드가 0이며 정확한 성공 marker 또는 구조화 결과가 있다.
- 허용하지 않은 script, parse, resource load 오류가 없다.
- 요청한 variant와 검사 수가 실제 실행 결과에 대응한다.
- 결과와 로그 지문이 검사 입력에 연결된다.

실패와 timeout 로그도 보존한다. 종료할 때는 해당 실행이 시작한 프로세스 ID와 시작 시각을 확인하고 그 프로세스만 종료한다. 기존 증거 디렉터리를 덮어쓰지 않으며 실행 중인 다른 프로젝트를 종료하지 않는다.

## 결과 재사용

재사용은 두 단계로 도입한다. 첫 단계는 **동일 입력에서 완료한 검사와 중복 포함 검사 제거**다. 두 번째는 입력 의존성이 검증된 suite에 한해 작업 스냅샷이 달라도 필요한 입력이 같을 때 재사용하는 것이다.

재사용 키에는 suite와 variant, 입력 의존성 전체 지문, fixture와 테스트 및 runner, 엔진, 필요한 템플릿과 플랫폼 조건, 프로필과 영향 규칙의 버전을 포함한다. 실행 receipt와 로그 hash를 함께 확인한다. 의존성이 불완전한 suite는 전체 게임 입력을 키로 사용해 보수적으로 판정한다.

| 상황 | 판정 |
| --- | --- |
| 같은 입력과 환경의 정상 완료 결과 | 범위가 맞으면 REUSED_PASS |
| README만 바뀌고 게임 입력은 동일 | 의존성 확인된 게임 suite는 재사용 가능 |
| 테스트나 fixture 또는 필수 개발 인자 변경 | 해당 검사 재실행 |
| 엔진, 플랫폼 조건 또는 관련 설정 변경 | 영향 검사 재실행 |
| 불완전한 결과, timeout, hash 불일치 | 재사용 불가 |
| 원자료가 사라지거나 절대 경로를 복원할 수 없음 | 재사용 불가 |
| 성능 인수, 물리 입력과 실행 환경에 민감한 검사 | 기본 재실행, 조건별 별도 정책 |

최종 판정은 `PASS`, `REUSED_PASS`, `FAIL`, `NOT_RUN`으로 구분한다. 선택하지 않은 항목의 이유는 별도로 적는다. 실행되지 않은 검사를 PASS로 출력하지 않는다.

현재 [수첩 합집합 감사](../scripts/audit_notebook_runtime_union.ps1)는 전체 `res://scripts/**/*.gd`의 소스 지문을 확인한다. 이 소스가 바뀌면 기존 합집합 증거를 재사용하지 않는다. 국소 regression의 재사용과 공식 생산자 커버리지 증거의 갱신은 각각의 계약을 따른다.

전체 감사의 최신 지문을 유지하기 위해 매 개발 수정마다 모든 생산자를 다시 실행하는 규칙은 두지 않는다. 검색 입력만 바뀌면 해당 경로를 검사하고, 과거 전체 감사는 이전 스냅샷의 근거로 남긴다. 최신 전체 감사는 통합 또는 마일스톤의 요구 범위에 맞춰 생성한다. 결과에는 `full_audit_fresh: false`처럼 최신 여부를 별도 표시하고 국소 PASS와 혼동하지 않는다.

## 여러 AI의 작업 계약

작업마다 task-key, 기준 커밋, 작업 경로, 수정 소유 파일, 읽기 범위, 완료 조건, 허용 명령, 필요한 검증과 인계 위치를 전달한다. 모델과 대화 식별자는 실행 추적용이며 작업 의미를 소유하지 않는다.

공유 파일 수정 요청은 조정 AI에게 전달하고 그 파일의 담당 작업에서 반영한다. 서로 다른 worktree여도 같은 공유 파일의 의미 충돌은 남으므로 파일 분리만으로 충돌 방지가 완료됐다고 판단하지 않는다.

통합 절차는 다음과 같다.

1. 각 구현 AI가 변경과 완료 조건, 검사 결과를 인계한다.
2. 검토 AI가 실제 diff와 누락된 영향 및 계약 변경을 확인한다.
3. 조정 AI가 정해진 순서로 변경을 통합한다.
4. 통합 결과의 새 스냅샷을 만들고 영향 합집합을 계산한다.
5. 그 입력에 유효한 검사를 재사용하고 나머지를 실행한다.
6. 인계를 갱신하고 검토 가능한 PR 초안을 만든다.

같은 작업 트리에 여러 독립 작성자가 있으면 자동 반영을 시작하기 전에 범위 중첩을 확인한다. 격리 worktree 생성 시 사용자 미커밋 수정이 자동 포함되지 않는 점도 작업 계약에 명시한다.

## 자동 이슈 선택과 외부 반영

후속 단계의 자동 선택 조건은 READY, 해결된 선행 작업, 명확한 완료 조건, 허용된 유형과 시스템, 수정 소유권 확보로 제안한다. 운영 중요도와 일정은 Project 값에서 읽는다. 사용자 승인 범위가 바뀌면 이후 선택부터 적용한다.

조회 실패나 인증 실패는 구현 실패와 구분한다. 외부 반영에는 작업 키와 대상 ID, 마지막 확인 상태를 기록해 재개 시 기존 이슈와 PR을 먼저 찾는다. 결과가 불확실한 생성 요청은 조회로 확인한 뒤 재시도한다.

첫 자동화는 draft PR 작성까지로 한정해 시범한다. 병합과 제품 엔진 채택, rollout 및 배포는 해당 사용자 지시와 제품 검증 조건에 따른다. 팀 전달과 알림은 승인된 수신처와 발송 범위를 사용한다.

## 인수 시나리오

| 시나리오 | 기대 결과 |
| --- | --- |
| 이전 대화 없는 AI가 작업 재개 | 목표와 마지막 결정, 기존 수정 및 다음 행동을 복원 |
| README의 일반 문구만 변경 | 문서 검사 선택, Godot 전편 검사 제외 |
| 수첩 query와 하위 search를 동시에 요구 | 조건이 같으면 부모 한 번으로 포함 검사 처리 |
| 수첩 표시와 저장 기능을 동시에 변경 | 두 시스템과 공유 소비자 검증 합집합 |
| 새 파일과 삭제 또는 이름 변경 | 이전 경로도 반영, 미분류 항목 표시와 검증 확대 |
| 저장 코드 변경 | 국소 UI 검사만으로 완료하지 않고 복구 및 주요 소비자 확대 |
| 검사 직후 관련 테스트 코드 수정 | 이전 결과 재사용 거부 |
| 로그에 PASS가 있지만 종료 코드 실패 또는 fatal 오류 | FAIL |
| 한 실행이 timeout되고 다른 실행이 진행 중 | 해당 실행만 종료, 양쪽 근거 보존 |
| 두 AI가 공유 파일 수정 | 중첩 표시와 담당 조정, 조용한 덮어쓰기 금지 |
| 검사 중 원본 작업 트리 변경 | 결과는 고정 복사본 기준, 최신 작업에는 재계획 |
| 전체 소스 지문이 다른 수첩 감사 로그 | 오래된 합집합 근거 거부 |
| GitHub 생성 결과가 불확실 | 기존 생성 여부 조회, 중복 생성 방지 |

검증 선택 규칙 자체는 고정된 변경 파일 fixture로 검사한다. 이는 영향 누락과 위험한 재사용을 막기 위한 도구 테스트다. 단순 문서와 체크리스트의 내용을 그대로 반복하는 테스트는 추가하지 않는다.

## 첫 구축 순서

1. 현재 상태와 주요 정본을 연결하고 짧은 안내 및 작업 형식을 만든다.
2. 기존 CLI와 부모 및 하위 suite를 대조해 테스트 목록을 확정한다.
3. `context`와 읽기 전용 `plan`을 구현해 예시 변경에 적용한다.
4. 실행별 격리와 timeout 및 공통 receipt를 붙인다.
5. 제한된 비교 실험 후 `affected`를 개발 기본값으로 적용한다.
6. 동일 입력 재사용과 독립 AI 인계를 시범한다.

첫 버전이 성공하면 실제 사용 시간과 누락 사례로 다음 범위를 정한다. 복잡한 테스트 분해, 여러 공급자 어댑터와 GUI는 그 결과에 따라 별도 작업으로 추진한다.
