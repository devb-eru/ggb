# GGB 작업 현황 대시보드

## 1. 목적과 정본

[GGB Production](https://github.com/users/devb-eru/projects/1)은 전 팀원이 현재 작업을 확인하는 운영 대시보드다. 운영 책임자는 `beru`이며, 각 작업 책임자는 자신이 맡은 항목의 상태와 다음 행동을 최신으로 유지한다.

대시보드는 GitHub Project 필드를 직접 읽어 보여준다. 별도 문서, 스프레드시트 또는 데이터베이스에 현재 수치를 복제하지 않는다. 따라서 필터 결과와 항목 수는 Project를 열 때마다 최신 값으로 갱신되고, 저장소에는 지표 정의와 뷰 구성만 기록한다.

## 2. 핵심 지표

| 지표 | 계산 기준 | 판단 |
| --- | --- | --- |
| 활성 작업 | `Status`가 `READY`, `IN_PROGRESS`, `REVIEW`, `BLOCKED` | 지금 누군가가 행동하거나 판단해야 하는 작업 |
| 차단 | `Status = BLOCKED` | `차단 원인`과 `차단 해제 조건`을 함께 확인 |
| 지연 | 활성 작업이면서 `목표일 < @today` | 목표일이 비어 있는 항목은 지연 수에 포함하지 않고 데이터 누락으로 처리 |
| 검토 대기 | `Status = REVIEW` | `Updated`가 오래된 순으로 먼저 확인 |

모든 날짜의 운영 기준은 KST다. `@today`를 사용하는 `지연` 뷰는 GitHub가 해석하는 현재 날짜에 따라 바뀌므로, 자정 경계에서 결과가 의심되면 KST 날짜를 명시해 다시 확인한다.

`Updated`는 REVIEW 진입 시각이 아니라 Issue 또는 Project 항목의 최근 갱신 시각이다. 따라서 `검토 대기` 뷰에서는 오래 멈춘 후보를 찾는 정렬 기준으로만 사용한다. 금요일 자동 안건의 정확한 24시간 대기는 Project 5분 감시 캐시에 보존한 상태 진입 시각으로 계산한다.

## 3. 저장 뷰

| 뷰 | 레이아웃 | 필터 | 그룹·정렬 | 주 표시 정보 |
| --- | --- | --- | --- | --- |
| `전체` | Table | 없음 | 수동 | 상태, 우선순위, 유형, 실제 담당자, 팀, 마일스톤, 시작일, 목표일, 차단 원인, 검증 근거 |
| `활성` | Table | `status:IN_PROGRESS,READY,BLOCKED,REVIEW` | 우선순위 오름차순 | 실제 담당자, 팀, 마일스톤, 목표일, 차단 원인, 검증 근거 |
| `차단` | Table | `status:BLOCKED` | 목표일 오름차순 | 실제 담당자, 목표일, 차단 원인, 차단 해제 조건 |
| `검토 대기` | Table | `status:REVIEW` | `Updated` 오름차순 | 검증 근거, Reviewers, Linked pull requests |
| `마일스톤` | Roadmap | `status:BACKLOG,READY,IN_PROGRESS,REVIEW,BLOCKED has:milestone` | Milestone 그룹 | `시작일`부터 `목표일`까지의 일정 막대 |
| `팀별` | Table | `status:READY,IN_PROGRESS,REVIEW,BLOCKED` | `담당 팀` 그룹 | 실제 담당자, 상태, 우선순위, 목표일, 마일스톤 |
| `담당자` | Table | `status:READY,IN_PROGRESS,REVIEW,BLOCKED` | `실제 담당자` 그룹 | 상태, 우선순위, 팀, 목표일, 마일스톤, 차단 원인 |
| `지연` | Table | `status:READY,IN_PROGRESS,REVIEW,BLOCKED "목표일":<@today` | 목표일 오름차순 | 상태, 우선순위, 실제 담당자, 팀, 마일스톤, 차단 원인 |

기존 `오늘` 뷰는 날짜 조건이 아니라 모든 활성 상태를 보여주고 있었으므로 `활성`으로 이름을 바꿨다. `팀별`과 `담당자`는 값이 없는 항목도 별도 빈 그룹으로 드러내기 위해 `has:` 조건을 사용하지 않는다.

## 4. 데이터 품질 규칙

활성 작업은 다음 값을 모두 가져야 한다.

- `Status`, `우선순위`, `유형`
- `실제 담당자`, `담당 팀`
- `Milestone`, `시작일`, `목표일`
- 완료 조건을 확인할 Issue 본문

상태별 추가 필수값은 다음과 같다.

- `BLOCKED`: `차단 원인`, `차단 해제 조건`
- `REVIEW`: PR·commit·QA·빌드 중 하나 이상의 `검증 근거`
- `DONE`: 최종 검증 근거와 닫힌 Issue

`Assignees`는 저장소를 조작하는 GitHub 계정이고 `실제 담당자`는 실제 작업 책임자다. 담당자별 현황은 반드시 `실제 담당자`로 집계한다. Issue의 열림·닫힘 상태도 Project `Status`를 대신하지 않는다.

## 5. 사용 순서

1. 작업을 시작할 때 `Status`, 실제 담당자, 팀, 마일스톤, 시작일과 목표일을 입력한다.
2. 매일 `활성`에서 P0·P1과 가까운 목표일을 확인한다.
3. `차단`에서 원인과 해제 조건, `검토 대기`에서 오래된 검증 요청을 처리한다.
4. 담당 충돌은 `담당자`, 팀 간 전달은 `팀별`, 일정 충돌은 `마일스톤`에서 확인한다.
5. `지연`이 생기면 목표일을 조용히 바꾸지 않고 Issue 댓글 또는 변경 이력에 이유를 남긴다.
6. 금요일 회의 전에는 빈 담당자·팀 그룹과 `전체`에서 목표일·마일스톤 누락을 함께 점검한다.

## 6. 검증과 변경

뷰를 바꿀 때는 이름, 레이아웃, 필터, 표시 필드, 그룹과 정렬을 함께 확인한다. 구성 변경 뒤에는 실제 활성 항목이 올바른 그룹에 나타나는지, `지연`이 목표일 전에는 비어 있는지, Roadmap이 `시작일`부터 `목표일`까지 표시하는지 확인한다.

대시보드 값은 GitHub Project에서만 수정한다. Discord 알림이나 회의 기록에서 발견한 변경도 먼저 Project에 반영하고, 변경 이유가 필요한 경우 관련 Issue에 남긴다.
